# تقييم نضج المنصة (Platform Maturity Benchmark)

## متى تستخدم هذا الـ skill
- طلب تقييم شامل "هل نظامنا بمستوى Shopify/منصات عالمية؟".
- قبل جولة استثمار أو شراكة تتطلب Due Diligence تقني.
- عند التخطيط لخارطة طريق منتج طويلة المدى (roadmap).
- **لا تستخدمه** لفحص شاشة واحدة أو باگ محدد — لذلك استخدم skills
  الأخرى (secrets-credentials-security, financial-data-consistency...
  إلخ) التي تفحص التفاصيل التنفيذية.

## منهجية التقييم: مستويات نضج لا حكم ثنائي
لكل بُعد أدناه، صنّف النظام بأحد أربع مستويات، ولا تكتفِ بـ"نعم/لا":
- **MVP**: يعمل لعميل واحد/قليل بإشراف يدوي مستمر، لا يتحمل نمواً سريعاً.
- **جاهز للنمو (Growth-Ready)**: يتحمل عشرات-مئات المستأجرين بأتمتة
  جزئية، لكن ينكسر أو يحتاج تدخل يدوي عند سيناريوهات حافة معينة.
  الأنظمة اللي راجعناها سابقاً (باگات العدّادات، الأسرار غير المشفّرة،
  مدير واحد بدون احتياطي) تضع النظام حالياً هنا تقريباً على أغلب الأبعاد.
- **جاهز للإنتاج (Production-Grade)**: يتحمل آلاف المستأجرين، أتمتة
  كاملة، مراقبة استباقية، يتعافى من الأعطال دون تدخل يدوي فوري.
- **مستوى مؤسسي (Enterprise-Tier)**: مستوى Shopify/BigCommerce —
  SLA رسمي معلن، امتثال قانوني موثّق (PCI-DSS, SOC 2)، منظومة تطبيقات
  خارجية (app ecosystem)، فرق مخصصة للموثوقية (SRE).

## أبعاد التقييم الإلزامية

### 1. المعمارية والتوسع (Architecture & Scalability)
- هل قاعدة البيانات مصممة لعزل مستأجرين بمقياس كبير (فهرسة على
  tenant_id، partitioning إذا لزم، أم كل شيء بجدول واحد مشترك بدون
  استراتيجية توسع واضحة)؟
- هل توجد طبقة تخزين مؤقت (caching layer: Redis أو ما يعادله) لتقليل
  ضغط قاعدة البيانات على العمليات المتكررة (كتالوج، أسعار)؟
- هل المهام الثقيلة/البطيئة (توليد تقارير، إرسال حملات جماعية، معالجة
  صور) تعمل عبر طابور مهام غير متزامن (job queue)، أم تحظر (block)
  الطلب الرئيسي حتى تنتهي؟
- هل يوجد حد معدل (rate limiting) لكل مستأجر يمنع "الجار المزعج"
  (noisy neighbor) من استهلاك موارد النظام على حساب مستأجرين آخرين؟
- هل تم اختبار تحمّل (load testing) فعلي تحت حمل يحاكي نمواً مستقبلياً،
  أم الأداء الحالي مبني فقط على التجربة الفعلية بعدد مستخدمين قليل؟

### 2. الموثوقية والعمليات (Reliability & Operations)
- هل يوجد نظام مراقبة استباقي (uptime monitoring, error tracking مثل
  Sentry) يُنبّه الفريق **قبل** أن يبلّغ عميل عن عطل، أم الاكتشاف
  حالياً تفاعلي (reactive) فقط عبر شكاوى العملاء؟
- هل توجد نسخ احتياطية (backups) مجدولة **ومُختبَرة فعلياً بالاستعادة**
  (restore drill)، لا فقط "موجودة نظرياً" بدون تحقق من قابليتها للعمل؟
- هل يوجد سجل هيكلي (structured logging) مركزي يسهّل تتبع مشكلة عبر
  عدة خدمات (Supabase, Cloudflare Workers, Edge Functions)، أم سجلات
  متفرقة بدون ربط؟
- هل يوجد أي شكل من "خطة تعافي من كوارث" (disaster recovery plan)
  موثّقة — ماذا يحدث لو انقطعت خدمة Supabase أو Cloudflare بالكامل؟
- هل يوجد status page علني (حتى لو بسيط) يوضّح حالة النظام للتجار؟

### 3. الأمان والامتثال القانوني (Security & Compliance)
راجع هذا البند بالتكامل مع `secrets-credentials-security` و
`multi-tenant-security` للتفاصيل التنفيذية، وأضف هنا الأبعاد الأوسع:
- **PCI-DSS**: هل بيانات البطاقات تمر مباشرة عبر خوادمك (نطاق امتثال
  عالٍ ومكلف)، أم تُحوَّل بالكامل لصفحة/حقول مستضافة من مزوّد الدفع
  (Tap Payments) بحيث لا تلمس خوادمك رقم البطاقة إطلاقاً (النهج الصحيح
  لمنصة SaaS صغيرة/متوسطة — تخفيض نطاق الامتثال المطلوب بشكل كبير)؟
- هل توجد سياسة خصوصية وشروط استخدام **مُراجَعة قانونياً فعلياً** (لا
  قالب عام منسوخ) تغطي التخزين متعدد المستأجرين وحقوق العملاء ببياناتهم؟
- هل يوجد سجل تدقيق (audit log) شامل يوثّق من غيّر ماذا ومتى على مستوى
  النظام بأكمله، لا فقط ببعض الميزات المعزولة (زي الولاء اللي راجعناه)؟
- هل تم إجراء اختبار اختراق (penetration test) خارجي مستقل ولو مرة
  واحدة، أم الفحص الأمني حتى الآن داخلي فقط؟

### 4. منظومة الامتداد والتكامل (Extensibility & API Ecosystem)
هذا أكبر فرق فعلي بين منصة "منتج مغلق" ومنصة "عالمية" مثل Shopify —
Shopify قوتها الحقيقية من آلاف التطبيقات الخارجية المبنية فوقها:
- هل يوجد API عام موثّق (REST/GraphQL) يقدر مطوّرون خارجيون يبنون
  فوقه تكاملات، أم كل التكامل حالياً داخلي فقط (Tap, Resend...) بدون
  واجهة مفتوحة للغير؟
- هل يوجد نظام webhooks عام يقدر التاجر يشترك فيه لأحداثه الخاصة
  (طلب جديد، تغيّر مخزون) لربطها بأنظمته الخارجية؟
- هل يوجد نظام قوالب/ثيمات (theme engine) يقدر مصمم خارجي يعدّل شكل
  المتجر بدون لمس الكود الأساسي، أم كل تخصيص بصري يتطلب تدخل مطوّرك أنت؟
- هل يوجد سياسة إصدارات API واضحة (versioning) وdeprecation policy
  تحمي المطوّرين الخارجيين من كسر تكاملاتهم عند أي تحديث؟

### 5. اكتمال الميزات التجارية الأساسية (Core Commerce Feature Completeness)
قارن قائمة ميزات نظامك بقائمة الميزات المتوقعة كحد أدنى بمنصة e-commerce
ناضجة (لا تحتاج كلها فوراً، لكن وثّق الفجوة بوعي):
- عملات ولغات متعددة فعلياً (لا عربي/إنجليزي فقط لواجهة الإدارة، بل
  دعم متاجر بعملات ولغات مختلفة كلياً حسب كل مستأجر).
- قواعد ضريبية متعددة الاختصاصات (لكل دولة/منطقة نسبتها وقواعدها).
- حاسبات شحن متكاملة مع شركات شحن فعلية (لا سعر شحن ثابت يدوي فقط).
- مخزون متعدد المواقع/المستودعات (multi-location inventory).
- ميزات B2B (تسعير بالجملة، حدود ائتمان، فواتير مؤجلة الدفع).
- اشتراكات ودفعات متكررة (subscriptions/recurring billing).
- نقاط بيع فعلية متصلة (POS) مع مزامنة مخزون لحظية أونلاين/أوفلاين.

### 6. تجربة المطوّر والتوثيق (Developer Experience & Documentation)
- هل يوجد توثيق API عام منشور (developer docs) بمستوى يقدر مطوّر
  خارجي يفهمه بدون تواصل مباشر معك؟
- هل يوجد changelog رسمي منشور لكل تحديث يؤثر على المطورين الخارجيين؟
- هل يوجد بيئة اختبار/sandbox منفصلة عن بيانات الإنتاج الفعلية للتجربة
  الآمنة قبل الاعتماد على أي تكامل جديد؟

### 7. الأداء وتحسين التحويل (Performance & Conversion Optimization)
- سرعة تحميل الواجهة الأمامية (Core Web Vitals: LCP, CLS, INP) —
  هل قِيست فعلياً بأداة مثل Lighthouse/PageSpeed، أم لم تُقَس بعد؟
- هل يوجد دفع كضيف (guest checkout) بدون إجبار إنشاء حساب، وهل خطوات
  الدفع أقل ما يمكن (single-page checkout مقابل عدة صفحات متتالية)؟
- هل الصور مُحسَّنة تلقائياً (تنسيقات حديثة، أحجام متجاوبة) أم تُرفَع
  وتُعرَض بحجمها الخام دون تحسين؟

## Output المطلوب من الـ agent (بطاقة تقييم النضج)
لكل بُعد من الأبعاد السبعة أعلاه، أنتج:
1. **المستوى الحالي** (MVP / جاهز للنمو / جاهز للإنتاج / مستوى مؤسسي)
   مع دليل ملموس من الكود/البنية يبرر هذا التصنيف، لا انطباعاً عاماً.
2. **الفجوة المحددة** للوصول للمستوى التالي (لا القفز مباشرة لمستوى
   مؤسسي إذا النظام حالياً MVP — حدد الخطوة الوسيطة الواقعية).
3. **الأولوية** (بناءً على: ماذا يمنع النمو فعلياً الآن مقابل ماذا
   "يبدو ناقصاً" نظرياً لكن لا يعيق أي شيء حالياً).

اختتم بجدول ملخص واحد يعرض كل الأبعاد السبعة ومستواها جنباً لجنب،
وخارطة طريق مرحلية مقترحة (3 مراحل: الأشهر 1-3، 4-9، 10+) بدل قائمة
مهام مسطحة بلا ترتيب زمني واقعي.
