# منطق الطلبات والمخزون (Order & Inventory Logic)

## متى تستخدم هذا الـ skill
- إضافة أو تعديل أي order status جديدة.
- أي منطق يخص حساب المخزون المتاح (available stock).
- أي شاشة تعرض قائمة طلبات، فواتير، أو منتجات.
- أي تقرير يعتمد على حالة الطلب أو المخزون.

## خطوات الفحص الإلزامية

### 1. فحص اكتمال دورة حياة الطلب (Order Lifecycle)
تأكد إن كل حالة طلب لها:
- انتقال واضح ومسموح للحالة التالية (state machine محددة، مو حرية تنقل عشوائية).
- تاريخ/وقت متوقع مرتبط بها إذا كانت تتطلب زمن (مثال: "تجهيز الطلب"
  يحتاج تاريخ تسليم متوقع، لا يكفي عرض الحالة فقط بدون ETA).
- تمييز واضح بين حالة عامة (generic status) وحالة مخصصة لنوع منتج معين
  (custom status)، بحيث لا تُعامَل كنفس الشيء بالتقارير أو الفلاتر.

### 2. فحص حالة الدفع مقابل حالة التنفيذ
هذان حقلان مختلفان يجب ألا يختلطا بصرياً ولا منطقياً:
- **حالة الدفع**: مدفوع / مدفوع جزئياً / غير مدفوع / مسترجع.
- **حالة التنفيذ/الشحن**: قيد التجهيز / تم الشحن / تم التسليم / ملغى.
تأكد أن النظام يمنع تناقضات منطقية، مثل طلب "تم التسليم" لكن حالة الدفع
"غير مدفوع" بدون تنبيه صريح للتاجر (هذا مؤشر خطر مالي حقيقي، لا يمر بصمت).

### 3. فحص منطق المخزون المنخفض والنافد
- عرّف threshold واضح لكل منتج ("مخزون منخفض" = أقل من كم وحدة؟) وتأكد
  إنه قابل للتخصيص لكل tenant وليس رقم ثابت بالكود.
- إذا نسبة كبيرة من الكتالوج (مثلاً أكثر من 50%) ظهرت "منخفضة" بنفس
  اللحظة، هذا يستحق تنبيه استباقي بارز في الداشبورد الرئيسية، ليس فقط
  داخل تبويب المخزون المدفون.
- تأكد إن حساب "الوحدات المتبقية" يأخذ بعين الاعتبار الطلبات المعلقة
  (pending orders) لتفادي oversell — لا يكفي حساب المخزون الفعلي فقط
  دون طرح الكميات المحجوزة بطلبات لم تكتمل بعد.

### 4. فحص المنتجات المخفية/غير النشطة
منتج بحالة "مخفي" أو "غير نشط" = مبيعات مفقودة محتملة. تأكد من:
- سبب الإخفاء موثق (نفاد مخزون؟ قرار يدوي من التاجر؟ مسودة لم تُنشر؟).
- تنبيه استباقي للتاجر لو عدد كبير من المنتجات مخفي دون سبب واضح
  (مثال: "5 من أصل 10 منتجات مخفية — تبي تراجعها؟") بدل الصمت الكامل.

### 5. فحص ربط بيانات العميل بالطلب
- عنوان التوصيل من أحدث طلب مكتمل يجب أن يُحفظ تلقائياً كـ"عنوان
  افتراضي" للعميل لإعادة الاستخدام، لا يبقى فارغاً رغم وجود طلبات سابقة.
- تصنيف العميل (جديد/متكرر/VIP) يجب أن يكون له معايير موثقة وواضحة
  (كم طلب = متكرر؟ كم إنفاق = VIP؟) وتُختبر بسيناريوهات حقيقية، لا تبقى
  فارغة صفر لكل الشرائح رغم وجود عملاء وطلبات فعلية.

## Output المطلوب من الـ agent
1. مخطط state machine كامل لحالات الطلب المكتشفة بالكود، مع أي انتقال
   غير منطقي أو مفقود.
2. أي تعارض مكتشف بين حالة دفع وحالة تنفيذ.
3. تقرير عن منطق المخزون المنخفض/النافد وهل يحسب الطلبات المعلقة أم لا.
4. قائمة بأي منتجات مخفية بدون سبب موثق، مع اقتراح تنبيه استباقي.
