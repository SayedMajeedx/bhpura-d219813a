# أمان تخزين مفاتيح API والأسرار (Secrets & Credentials Security)

## متى تستخدم هذا الـ skill
- أي صفحة "تكاملات/ربط/webhooks" تعرض أو تحفظ API keys.
- أي feature يربط خدمة دفع (Tap, Stripe) أو بريد (Resend, SendPulse)
  أو ذكاء اصطناعي (Gemini, OpenAI) عبر مفتاح يُدخله التاجر.
- أي بانر تحذيري موجود بالفعل بالواجهة يذكر "بيانات غير مشفّرة" أو
  "لا تلصق أسرار الإنتاج" — هذا مؤشر أكيد على استخدام هذا الـ skill فوراً.

## خطوات الفحص الإلزامية

### 1. فحص التشفير عند التخزين (Encryption at Rest) — أولوية قصوى
أي مفتاح API أو webhook secret يُخزَّن بقاعدة البيانات يجب أن يكون
**مشفّراً** (encrypted at rest)، وليس نص عادي (plaintext) حتى لو كان
مقنّعاً بالواجهة فقط. إذا وجدت بالواجهة تحذيراً صريحاً يقول إن البيانات
"تُحفظ كما هي" أو "لا تلصق أسرار إنتاج قبل تفعيل التشفير"، هذا يعني:
- النظام **يعترف بنفسه** بغياب التشفير الفعلي — هذا Blocker حرج يجب
  حله فوراً، وليس لاحقاً، قبل السماح بأي استخدام إنتاجي.
- تحقق فوراً من عدد المستأجرين (tenants) الذين لديهم مفاتيح مُدخلة
  فعلياً رغم التحذير — إذا وُجد أي مفتاح يشبه صيغة مفتاح إنتاج حقيقي
  (live/production pattern، وليس test/sandbox)، هذا يستدعي تنبيه فوري
  للتاجر لتدوير (rotate) المفتاح من لوحة المزوّد الأصلي.
- الحل الصحيح: تشفير على مستوى العمود (column-level encryption) أو
  استخدام خدمة إدارة أسرار مخصصة (secrets manager / vault) بدل حفظها
  مباشرة بجدول قاعدة البيانات الرئيسي.

### 2. فحص قواعد الإخفاء بالعرض (Display Masking Rules)
مفتاح مقنّع جزئياً (مثال: `sk_t••••••0xut`) لا يزال يكشف:
- البادئة (prefix) التي تكشف نوع البيئة (test/live) ونوع المزوّد.
- اللاحقة (suffix) التي قد تكفي لتضييق نطاق التخمين أو المطابقة مع
  تسريبات بيانات أخرى.
تأكد من أن قاعدة الإخفاء تُظهر **الحد الأدنى الضروري فقط** للتعرّف على
المفتاح (مثال: آخر 4 أحرف فقط، بدون بادئة تكشف نوع البيئة)، وأن كامل
المفتاح لا يُرسَل أبداً للواجهة الأمامية (frontend) حتى لو كان الإخفاء
يحدث بجافاسكربت من جهة العميل — يجب أن يحدث الإخفاء من جهة السيرفر.

### 3. فحص التدقيق وإدارة دورة حياة المفتاح
لكل تكامل مُفعَّل، تحقق من وجود:
- تاريخ الإضافة/آخر تعديل (created_at / last_rotated_at) ظاهر للتاجر.
- زر "تدوير المفتاح" (rotate) أو "إبطال" (revoke) صريح وسهل الوصول.
- سجل تدقيق (audit log) لمن أضاف/عدّل كل مفتاح ومتى.

### 4. فحص أدوات الاختبار المكشوفة (Exposed Test Tools)
أي أداة اختبار مباشرة داخل صفحة إعدادات رئيسية (مثال: أداة إرسال/تحقق
OTP تجريبية) يجب أن:
- تكون محمية بـ rate limiting صارم يمنع إرسال متكرر لنفس الرقم
  (لتفادي إساءة استخدام كـSMS/WhatsApp bombing تجاه أرقام حقيقية).
- تكون محدودة الصلاحية لدور admin فقط، ومفصولة بوضوح بصرياً عن
  إعدادات الإنتاج الحقيقية (مثال: قسم منفصل واضح "بيئة الاختبار فقط").
- لا تُستخدم فعلياً لإرسال رسائل حقيقية بدون تأكيد إضافي صريح.

### 5. فحص تسريب المعرّفات عبر الروابط العامة
أي رابط webhook عام (public URL) يحتوي معرّف المستأجر (tenant UUID)
يجب أن يُفحص لمعرفة: هل نفس الـ UUID يتكرر بروابط أخرى مكشوفة بالنظام
(شعارات، أيقونات، ملفات مرفوعة)؟ التكرار المتعدد لنفس المعرّف عبر
سياقات مختلفة مكشوفة يزيد من قابلية الربط والاستهداف (correlation
risk)، حتى لو كان كل رابط بمفرده غير قابل للتخمين مباشرة.

## Output المطلوب من الـ agent
1. تأكيد فوري (نعم/لا): هل التشفير at-rest مفعّل فعلياً لكل الأسرار
   المخزّنة؟ إذا لا، هذا Blocker يوضع بأعلى التقرير مباشرة.
2. قائمة بأي مفتاح يشبه صيغة إنتاج حقيقي مُدخل فعلياً رغم تحذير النظام.
3. تقييم قاعدة الإخفاء الحالية وهل تكشف بادئة/لاحقة كافية للتخمين.
4. تأكيد وجود/عدم وجود آلية rotate/revoke وaudit log لكل مفتاح.
5. تقييم أي أداة اختبار مكشوفة (زي OTP) من ناحية rate limiting والصلاحيات.
