# تنفيذ وثائق الـ Handoff (Handoff Plan Execution)

## متى تستخدم هذا الـ skill

- أي مهمة تبدأ بـ "نفّذ الخطة في `docs/…-plan.md`".
- أي مهمة متعددة المراحل (≥ 2 PR) تمس الإعدادات، الستور فرونت، أو
  إنشاء البراندات.

## قبل أول سطر كود

1. **اقرأ الوثيقة كاملة** — كل الأقسام بما فيها "ما لا يجب فعله"
   و"قرارات المالك" و"تعريف الاكتمال". لا تبدأ من §3 لأنه "الجزء العملي".
2. **سجّل الـ baseline** على commit البداية والصقه في وصف أول PR:
   ```bash
   git rev-parse --short HEAD
   npm run typecheck
   npx vitest run
   npm run lint
   npm run db:migrations:check
   ```
   الفشل الموجود قبلك ليس مسؤوليتك، لكن **أي فشل جديد** مسؤوليتك.
3. **تحقق من كل مرجع `file:line`** قبل الاعتماد عليه — الوثائق تُكتب عند
   commit معيّن (مذكور في رأسها) والأرقام تتحرك. استخدم `grep -n` لإعادة
   إيجاد الموضع بالاسم لا بالرقم.
4. **اقرأ الـ skills المرجعية** التي تذكرها الوثيقة، و`.agents/rules/AGENTS.md`
   إذا كنت ستلمس أي واجهة.
5. إذا كانت الوثيقة تذكر وثيقة سابقة كشرط (prerequisite)، تأكد أنها
   مُدمجة في `main` فعلاً (`git log --oneline main | grep …`). إن لم تكن،
   توقف واسأل المالك — لا تبنِ فوق فرع غير مدمج.

## أثناء التنفيذ

- **PR واحد لكل مرحلة** بالترتيب المذكور. لا تدمج مرحلتين "لتوفير الوقت".
- **الفرع** بالاسم المذكور في جدول الـ PRs.
- **النطاق ثابت**: لا تضف ميزات لم تُذكر، ولا تحذف ما ذُكر. إذا رأيت شيئاً
  يستحق الإصلاح خارج النطاق، سجّله في قسم "ملاحظات خارج النطاق" في وصف
  الـ PR ولا تنفّذه.
- **قرارات المالك (§8 في كل وثيقة) نهائية** — لا تعِد طرحها ولا تنفّذ
  عكسها حتى لو رأيت حلاً "أفضل". اذكر رأيك في الـ PR كملاحظة فقط.
- **الانحرافات**: إذا اضطررت للانحراف عن الخطة (مرجع اختفى، دالة تغيّرت،
  قيد تقني)، وثّق في وصف الـ PR: ما الذي قالته الخطة، ما الذي فعلته، ولماذا.
- **الملفات الكبيرة**: الوثائق تمنع تضخيم ملفات محددة (مثل
  `admin.b.$slug.settings.tsx`, `$slug.product.$id.tsx`). كل UI جديد =
  ملف مكوّن جديد. راجع `refactor-safety` عند النقل.
- **الـ migrations**: راجع `migration-hygiene`. البادئة الزمنية يجب أن
  تكون أحدث من آخر ملف موجود (`ls supabase/migrations | tail -1`) حتى لو
  كان تاريخه في المستقبل. append-only دائماً.
- **النصوص**: كل نص جديد ثنائي اللغة (ar/en). راجع `rtl-arabic-consistency`.
- **الاختبارات**: كل وحدة نقية جديدة لها اختبار vitest في `tests/`. راجع
  `test-quality-gate`. لا تُضعف أي threshold موجود في Playwright audits.

## قبل فتح كل PR

```bash
npm run check                 # typecheck + lint + format:check + test
npm run db:migrations:check   # إن لمست migrations
npx playwright test tests/<relevant>.spec.ts
```

وصف الـ PR يحتوي إلزامياً:

1. رقم المرحلة والقسم (§) المنفَّذ.
2. الـ baseline قبل/بعد (أرقام الاختبارات والـ typecheck).
3. قائمة الملفات المضافة/المعدّلة/المحذوفة.
4. جدول "بند الخطة → commit" (مثل `D1 → abc123`).
5. الانحرافات وسببها.
6. لقطات شاشة (جوال 375 + سطح مكتب 1280) لأي تغيير مرئي، عربي وإنجليزي.
7. خطوات التحقق اليدوي التي نفّذتها فعلاً (لا تكتب ما لم تفعله).

## بعد آخر مرحلة

- راجع "تعريف الاكتمال" بنداً بنداً وضع ✅/❌ مع الدليل.
- حدّث الوثيقة نفسها بحالة الإنجاز (قسم "Status" في الأعلى) والتاريخ.
- أنشئ/حدّث وثيقة المعمارية المطلوبة (`docs/settings-architecture.md`،
  `docs/storefront-architecture.md`).

## علامات الخطر (توقف واسأل)

- الخطة تطلب حذف/إعادة تسمية عمود في قاعدة البيانات (لا تفعل — الخطط
  هنا append-only دائماً؛ إن بدا عكس ذلك فهو خطأ في فهمك).
- تحتاج مكتبة جديدة لم تذكرها الخطة.
- تغيير في منطق السلة/الدفع/المخزون/التسعير لم يُذكر صراحة.
- اختبار موجود يفشل بسبب تغييرك وتميل لتعديل الاختبار بدل الكود.
- البراند `PURA_BRAND_ID` يتأثر بأي عملية آلية (مزامنة تصنيفات، backfill).
