# دقة صلاحيات الفريق وإدارة المخاطر (Team Roles & Permission Granularity)

## متى تستخدم هذا الـ skill
- أي صفحة "فريق العمل والصلاحيات" أو إدارة أعضاء وأدوار.
- أي منطق role-based access control (RBAC) جديد أو معدّل.
- أي مستأجر (tenant) لديه عضو فريق واحد فقط بدور "مدير/admin" كامل.

## خطوات الفحص الإلزامية

### 1. فحص دقة مصفوفة الصلاحيات (Permission Matrix Granularity)
تحقق من أن الأدوار المتاحة ليست ثنائية فقط (مدير = كل شيء، موظف =
لا شيء)، بل تدعم صلاحيات دقيقة قابلة للتخصيص لكل وحدة عمل على حدة:
- عرض/تعديل الطلبات.
- عرض/تعديل المخزون والمنتجات.
- عرض البيانات المالية (مصاريف، إيرادات، مفاتيح API).
- إدارة أعضاء الفريق أنفسهم (لا يجب أن يقدر موظف عادي يضيف/يحذف مدير).
إذا كان النظام يدعم دورين ثابتين فقط بدون تخصيص، وثّق هذا كقيد يستحق
معالجة خصوصاً لمتاجر تكبر وتحتاج أدوار متخصصة (محاسب يشوف مالية بس،
موظف مخزون يشوف طلبات بس).

### 2. فحص مخاطر نقطة الفشل الواحدة (Single Point of Failure)
إذا كان يوجد **عضو فريق واحد فقط** بدور المدير الكامل:
- وثّق هذا كمخاطرة تشغيلية عالية: فقدان الوصول لهذا الحساب (نسيان
  كلمة سر، ترك الشركة، حظر الحساب) يعني فقدان كامل السيطرة على المتجر.
- تحقق من وجود آلية استرداد وصول طارئة على مستوى المنصة نفسها (لا على
  مستوى المستأجر) — مثال: فريق دعم المنصة يقدر يتحقق من هوية صاحب
  النشاط ويعيد له الوصول بمسار موثّق.
- اقترح للتاجر إضافة مدير احتياطي ثانٍ كممارسة أفضل، مو إجبارية تقنية.

### 3. فحص اكتمال بيانات التواصل لكل عضو
تأكد من أن كل عضو فريق لديه **قناتي تواصل مستقلتين على الأقل** (بريد
+ هاتف)، خصوصاً للأدوار عالية الصلاحية (مدير). عضو بحقل هاتف "غير
محدد" يعني قناة تواصل طارئة واحدة فقط (البريد)، وهذا يقلل فرص التواصل
السريع وقت حادثة أمنية أو تشغيلية عاجلة.

### 4. فحص الحسابات المعطّلة وأثرها
لأي عضو بحالة "معطّل"، تحقق من:
- أن كل الجلسات النشطة (active sessions) والتوكنز الخاصة به تُبطَل
  فوراً عند التعطيل، لا تنتظر انتهاء صلاحيتها الطبيعية.
- أن الإجراءات السابقة المسجّلة باسمه (audit log) تبقى محفوظة للتتبع
  حتى بعد تعطيل حسابه.

### 5. فحص تسلسل صلاحية تعديل الأدوار نفسها
تأكد من أن تعديل دور عضو آخر (ترقية لمدير، تخفيض لموظف) يتطلب صلاحية
مدير فقط، وأن عضو لا يقدر يرفّع صلاحيته الخاصة بنفسه (self-privilege
escalation) عبر أي ثغرة بواجهة أو API مباشر.

## Output المطلوب من الـ agent
1. توثيق مصفوفة الصلاحيات الفعلية المتاحة بالنظام: هل هي ثنائية أم
   دقيقة قابلة للتخصيص لكل وحدة عمل؟
2. تنبيه صريح لأي مستأجر لديه مدير واحد فقط بدون احتياطي، مع اقتراح.
3. قائمة بأي عضو فريق ناقص قناة تواصل بديلة (هاتف/بريد).
4. تأكيد إبطال الجلسات فوراً عند تعطيل حساب، ومنع ترقية الصلاحية الذاتية.
