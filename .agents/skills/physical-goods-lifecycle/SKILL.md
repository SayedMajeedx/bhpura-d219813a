# دورة حياة البضاعة الفعلية (Physical Goods Lifecycle)

## متى تستخدم هذا الـ skill
- صفحة المرتجعات والاستبدال (returns center).
- صفحة الحاضنات/العُهد/القنسنمنت (consignment).
- أي شاشة فيها "قطع متبقية" أو "مخزون مستحق" مرتبط بطرف ثالث أو بعملية إرجاع.
- أي تقرير مالي مبني على عدّ قطع فعلية بحالات متعددة.

## خطوات الفحص الإلزامية

### 1. مطابقة العدّادات (Count Reconciliation) — أولوية قصوى
لأي صفحة فيها "إجمالي/متبقي" بكارت ملخص بالأعلى، **قارنه رقمياً** مع
مجموع الصفوف الفعلية بالجدول (بما فيها كل الصفحات، ليس فقط الصفحة
المعروضة). أي فرق بين الرقمين (مثال: كارت يقول 23 والجدول يقول 21)
هو **باگ حرج بمصدر بيانات مالي/بضاعة حقيقية** ويُصنَّف تلقائياً
"Blocker" — لا يُترك كـ"تحسين لاحق". أسباب شائعة:
- الكارت يحسب من cache/aggregate table لم يُحدَّث بعد آخر عملية بيع/إرجاع.
- الجدول يستثني صفوف بحالة معينة (مباعة، محذوفة) لكن الكارت لا يستثنيها.
- خطأ بمنطق COUNT بالـ query (JOIN مكرر يضاعف بعض الصفوف).
اكتب استعلام تحقق مباشر بقاعدة البيانات (`SELECT COUNT(*) ...`) وقارنه
يدوياً بالرقمين المعروضين لتحديد أيهما الخاطئ قبل اقتراح أي إصلاح.

### 2. فحص الإجراءات المزدوجة على نفس القطعة (Double-Action Risk)
لكل صف بجدول قطع فردية، تأكد إن أزرار الإجراء (مباعة/إرجاع/استرداد)
تتغيّر أو تُعطَّل (disabled) بناءً على الحالة الحالية للقطعة، بحيث:
- قطعة "مباعة بالفعل" لا يظهر لها زر "مباعة" فعّال مرة ثانية.
- قطعة "مرتجعة بالفعل" لا يقبل النظام إرجاعها مرتين (لتفادي استرداد مالي مضاعف).
لو الحالة الحالية للقطعة غير ظاهرة أصلاً بالجدول (عمود status مفقود)،
هذا بحد ذاته عيب يجب إضافته قبل أي شيء آخر.

### 3. فحص اكتمال بيانات الطرف الثالث (Third-Party Data Completeness)
لأي علاقة تجارية فيها التزام مالي على المتجر تجاه طرف خارجي (مورّد
حاضنة، عميل مرتجع)، تأكد من:
- وجود بيانات تواصل موثقة إجبارياً (لا يُسمح بحفظ سجل "حاضنة" أو
  "مرتجع معلّق" بمبلغ مالي > 0 بدون رقم هاتف أو بريد على الأقل).
- إذا كان المبلغ المستحق > 0 وبيانات التواصل فارغة، اعرض تنبيه واضح
  للتاجر بدل الصمت.

### 4. فحص انتقالات الحالة (Status Transitions)
لأي workflow متعدد المراحل (بانتظار المراجعة → مقبول → مستلم/قيد
الفحص → تم الاسترداد → مكتملة)، ارسم state machine كاملة وتأكد:
- لا يوجد انتقال يتخطى مرحلة إلزامية (مثال: من "بانتظار المراجعة"
  مباشرة إلى "تم الاسترداد" بدون مرور بـ"مقبول").
- كل مرحلة لها مسؤول واضح (من يقدر يغيّرها: النظام تلقائياً، الموظف،
  أم العميل نفسه عبر بوابة self-service؟).
- لا توجد مرحلة "ميتة" يمكن للطلب أن يعلق فيها بدون timeout/تنبيه.

### 5. فحص تنسيق الأكواد المرجعية
أكواد التتبع (كودنا الداخلي، كود الحاضنة الخارجي) يجب أن تتبع نمط
تسمية موحّد وقابل للتحقق (validation pattern)، وألا تُترك فارغة
("—") لبعض الصفوف بينما البقية معبّأة — هذا يصعّب التسوية المالية
اليدوية لاحقاً مع الطرف الثالث.

## Output المطلوب من الـ agent
1. نتيجة مطابقة العدّادات (كارت الملخص مقابل مجموع الجدول الفعلي)
   لكل صفحة تحتوي أرقام إجمالية، مع الاستعلام المستخدم للتحقق.
2. قائمة بأي زر إجراء يمكن الضغط عليه مرتين على نفس القطعة بدون منع.
3. قائمة بأي سجل التزام مالي (>0) بدون بيانات تواصل موثقة.
4. مخطط state machine كامل مع أي انتقال أو مرحلة غير منطقية.
