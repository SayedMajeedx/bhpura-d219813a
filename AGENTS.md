# AGENTS.md — Boutq OS Architecture & Contributor Guide

Welcome! This document is the primary entry point for AI agents and human engineers working on Boutq OS (`bhpura-d219813a`). Every statement here is verified against the codebase as of September 2026.

---

## 1. What Boutq Is

Boutq is a multi-tenant e-commerce and brand operations platform for GCC boutique brands.

- **Tenants / Brands**: Each merchant owns a brand scoped by `brand_id` and unique `slug` (e.g. `/pura`).
- **Surfaces**:
  - **Storefront (`src/routes/$slug.*.tsx`)**: Public shopping experience. Supports bilingual (AR/EN), RTL-first layout, currency formatting, and two sales modes (`storefront_mode`: `shop` for direct checkout, `catalog` for a showcase with WhatsApp inquiries and optional prices).
  - **Admin Panel (`src/routes/_authenticated/admin.b.$slug.*.tsx`)**: Authenticated back-office for catalog, inventory, orders, marketing, expenses, team, and settings.
  - **Super Admin (`src/routes/_authenticated/admin.super.*.tsx`)**: Platform operations, tenant provisioning, system health, and billing plans.
- **Storefront Engine (V1 vs V2)**: Governed by `storefront_design_version` (1 or 2) in `business_settings`.
  - V1: Classic stable layout with 1:1 product cards.
  - V2: Premium agency-grade experience with 3:4 cards, cinematic hero (`HeroV2`), quick add, color swatches, and vertical design presets (`editorial`, `fresh`, `tech`). See [`docs/storefront-architecture.md`](./docs/storefront-architecture.md).

## 2. Tech Stack & Runtimes

- **Web**: React 19.2, TanStack Start (Vinxi / Vite), Tailwind CSS v4, Lucide icons, Radix UI primitives.
- **Mobile (`apps/boutq-os-mobile/`)**: React 19.1, React Native 0.81, Expo 54, React Navigation.
- **Runtime Host**: Cloudflare Workers (SSR + edge functions) with Cloudflare R2 object storage.
- **Backend & Database**: Supabase (PostgreSQL 15, RLS tenant isolation, Auth, Storage, Deno Edge Functions).

## 5. "Where Do I Change X?" (Quick Reference)

- **Products & Catalog**:
  - Admin management: `src/features/inventory/` (`components/` for the product list, product editor and variant table; `hooks/` for data and mutations; `lib/` for pure, unit-tested rules). The route `src/routes/_authenticated/admin.b.$slug.inventory.tsx` only loads data and picks the tab. Shared inventory UI: `src/components/inventory/`
  - Storefront product page: `src/routes/$slug.product.$id.tsx` (composition) + `src/features/product-page/` (option rules, pricing, cart line, gallery, pickers). Priced options (an add-on in `customization_options`, or a listed choice of a product's select field whose text names a price, "Silk lining (+ 5 BHD)") are priced by the database from the store's own data, never from the browser's price: `storefront_line_customizations` (migration `20261011100000`, service role only) feeds the order builder, which charges (price + options) x quantity and writes `order_items.customizations` / `customization_total`. `fieldPriceDelta` (`lib/variant-options.ts`) is its twin for the product page and cart: free text a shopper types never carries a price (`tests/priced-options-migration.test.ts` runs both against each other)
  - What a shopper's choice adds (`lib/variant-options.ts`): **nothing is chosen for the shopper**. `chosenVariant` names a variant only once every option offered with more than one value is chosen (a product's only variant still is), `previewVariant` gives the photo while the choice is partial, and `choiceUnavailable` decides "notify me" (the chosen size has no piece, or nothing chosen and the product cannot be bought by the one availability rule). The page once took the first variant when nothing was chosen, so it opened on an out-of-stock size. The bundle ("Complete your order", `BundleOffer`, rules in `src/lib/cart/bundle-offer.ts`) adds only what one tap can name: the chosen in-stock piece (a made-to-order one in a ready size as `tailored: false`) and a second piece in its only variant or the shopper's size; it asks for the size first and steps aside while out of stock or made to order. Marketing consent at checkout starts unticked (`tests/storefront-choice-and-bundle.test.tsx`).
  - **The product page says only what is written, in the store's words** (`ProductAccordion`, rules in `features/product-page/lib/product-details.ts`): the description section shows only when there is one; the details section holds the product's own fields (`fabric_type` under the store's own word for its fabric axis, `occasion`) and the store's care text (`fabric_care_*`), titled by what it holds (`detailsSection`), and is left out when it holds nothing. It once printed "No additional description", told every fashion product to "hand wash cold or dry clean", and titled one store-wide text "Fragrance Notes". A vertical's words follow its family (`getVerticalVocabularyOverrides` over `verticalLineage`: abayas speak fashion's), and jewellery, home, gifts, print and digital have their own. What a product is for (`products.occasion`, the editor's four in `src/lib/product-occasion.ts`) is shown there and filtered on a listing (`occasions` in `src/lib/category-filters.ts`, `?occasion=`). On a phone's product page the bar at the foot asks about the product on WhatsApp (`AskOnWhatsAppButton`, the product's `inquiryUrl`, in a shop with WhatsApp on as in a catalog) and the floating button shows from `md` up only, as it sat over the page's own buttons. A print store's file is uploaded (`logo_upload` is a `file` field). `tests/product-details-section.test.tsx`, `tests/category-filters.test.ts`.
  - **What a product is, in its kind of store's facts** (`products.details`, migration `20261024120000`, run in a real Postgres by `tests/product-facts-migration.test.ts`): each vertical's set is `src/lib/product-facts.ts` (`factSet`, following the vertical's family like the vocabulary: a perfume's concentration, scent family, top, heart and base notes and longevity; beauty's key ingredients, skin type and what it is free from; food's ingredients, allergens, servings and keeping; coffee's origin, variety, process, roast, tasting notes and altitude; jewellery's metal, karat, weight, stones and certificate; home's dimensions, material and assembly; fashion's fit and what the model wears; gifts, print, digital and electronics theirs; none for the general store and services). The editor offers the store's set under the description (`ProductFactsFields`: a list typed as one line, choices as chips); what is saved is `cleanFacts` (known shapes, bounded; the column holds it an object of at most 8 KB). The product page draws them in the details section after the fabric and occasion (`productDetailLines`, `detailGroups`, `ProductDetailsBody`: a perfume's notes as a pyramid, a food's allergens first in a note of their own, a list's items as chips) and Google's data carries them as `additionalProperty` (`productHead`, the store's vertical from the layout). A fact the set does not offer (a store that changed its kind) is kept and not shown. Duplicating a product copies them. `tests/product-facts.test.ts`, `tests/product-facts-screens.test.tsx`. **A card says one fact under the name** (`CardFactLine`, `cardFact` by the set's `card` rule: a perfume's concentration and family, a coffee's origin and roast, a jewel's karat, metal and weight, a home piece's W × D × H, a food's servings; none for fashion and the general store), on both cards and the menu's rows (left out when empty: a card's price sits at its foot, `mt-auto`, so a row's prices line up without an empty line); the cards read `details` through the product selects and the home page through `get_storefront_page_data` (migration `20261024130000`, the live function with one key added, `tests/card-facts-migration.test.ts`). **A listing filters by the store's choice facts** (`filterableFacts`: a roast, a process, a concentration, a scent family, a metal, a karat, a skin type; never a food's allergens), product-level like occasion, in the address as `?f_<key>=` (`facts` in `src/lib/category-filters.ts`, a group per fact in `CategoryFilters`). `tests/card-facts.test.tsx`.
  - **A product's photo is one reading** (`productCover`, `hasProductPhoto` in `src/lib/product-photo.ts`: its main picture, else its gallery's first, else a size's): a product with none stays in the grid and its listing, drawn with the store's initials (`ProductPhotoPlaceholder`, never "No image"), and is left out of the home page's rails and the product page's recommendations (`homeMerchandising`, `useProductRecommendations`). A list's count is `catalogCount` / `shownOfTotal` (`src/lib/catalog-count.ts`: "12 منتجًا", "8 من 12"); a category page says it once, under its heading, and its filter and sort sit in the grid's own bar (`ProductGrid`'s `toolbar`). The phone's buy bar never cuts the price (`ProductMobileBuyBar`). `tests/storefront-polish.test.tsx`, `tests/home-products.test.ts`.
  - **The storefront promises only what the store said** (2026-10-24): the trust bar, until the merchant saves badges, shows only what the settings say (`storeFactBadges` in `src/lib/trust-badges.ts`: the payment methods that are on, delivery, pickup, digital delivery, free delivery at a zero fee), never a kind of store's claim, "fast", cash when unset or "256-bit SSL"; the editor starts from those same badges, and its "auto-generate" adds the vertical's line for the merchant to read and save. The brand story's points are the store's own (`homepage_editorial_sections.story_points`, `storyPoints`, edited under the story in the Home page group): none show until written, and the vertical's are only the editor's grey text. A hero slide whose headline is only the store's name gets a note in its settings (`storeNameHeadlineNote`). `tests/trust-badges-resolution.test.ts`, `tests/brand-story-defaults.test.tsx`, `tests/settings-home-page.test.tsx`.
  - Cards & presentation: `src/components/storefront/product-card.tsx` (`ProductCard` / `ProductCardV2`). **A product's photo on a card takes the store's shape** (`productCardRatio`, `PRODUCT_PHOTO_CLASS` in `src/lib/brand-templates/design-presets.ts`): the store's own (`business_settings.product_card_aspect_ratio`: 3:4, 4:5, 1:1 or 4:3; migration `20261023130000`, `ProductPhotoShapeField` in Product card & page), else its vertical's (`VERTICAL_DESIGN_PRESETS.productPhoto`: portrait for clothes, square for food, beauty, jewellery and most goods, landscape for home and services). Both cards and the grid's placeholders read it; never write a card's `aspect-[3/4]` by hand. The vertical presets hold only what is applied (the wizard's `radius`, the photo shape and the home layout); a preset name, grid, spacing and card style that nothing read were removed (`tests/brand-templates.test.ts`, `tests/product-card-photo-shape-migration.test.tsx`, `tests/storefront-engine-surfaces.test.tsx`)
  - **Reviews on each product's page** (migration `20261022100000`, run in a real Postgres on the live review functions by `tests/product-reviews-migration.test.ts`): a review is given for an order (`order_reviews`), so a product's reviews are those of the orders that held it. `storefront_product_reviews(slug, product)` (anon) gives the stars of every one (average, count, each star's count, what customers praise) and the words of those the customer let the store show (`show_on_store`, the box on the review form, never ticked for them; the discount does not depend on it) and the store did not hide (`hidden_at`, `hidden_by`; `set_order_review_hidden`, staff with `manage_customers`, from the Reviews page). **Hiding takes a review's words off the page, never its stars**, so it cannot raise a rating. Only a first name leaves the database. The reviews given before the form asked are shown (the owner's decision, 2026-10-22). The page reads it beside the product (`fetchProductReviews`, never rejects) and draws `ProductReviews` (rules in `features/product-page/lib/product-reviews.ts`, `arCount` now in `src/lib/arabic-count.ts`); its Google data carries the same stars (`aggregateRating`). `tests/product-reviews.test.tsx`, `tests/reviews-data-layer.test.ts`. **The thank-you discount for a review is the store's own** (migration `20261022110000`, `tests/store-review-reward-migration.test.ts`): one of its promo codes or none (`business_settings.review_reward_promo_id`, chosen on the Reviews page by staff who may change settings, `ReviewRewardCard`, registry owner `route:reviews`), given only while anyone can use it (`store_review_reward`: active, started, not ended, not one-use; its twin `reviewRewardUsable` in `src/lib/review-reward.ts`); the review page, the WhatsApp request (`reviewRequestMessage`) and the Reviews page say that store's offer (`rewardOffer`) or promise nothing. Every store once handed out THANKU10, a code only Pura had (`tests/review-reward.test.tsx`).
  - **The shopping feed** (Instagram / Facebook Shop through Meta Commerce Manager, and Google Merchant Center): the worker serves `/{slug}/products.xml` and `/products.xml` on a store's own host (`src/lib/seo/product-feed.server.ts`, beside the sitemap; `?lang=en` for English, Arabic by default), built on every fetch from the catalog by the pure `feedItems` / `feedXml` (`src/lib/seo/product-feed.ts`): one item per size, grouped under its product, linked to that size (`?variant=`, which the product page opens on: `linkedVariantId` in `useVariantSelectionSync`). **It says only what the storefront says**: a size's own price and sale, whether it can be bought now by the cards' own rule (`variantSellable` in `src/lib/product-availability.ts`, which `buyableVariants` reads too), the options in the store's words (`describeVariantAxes`). Left out: hidden products, services, packages, a size with no price or no picture; a store that hides its prices has no feed. The merchant copies the links from Integrations → Pixels (`ShoppingFeedCard`, `feedAddress`). **The product page's Google data agrees with it** (`productHead`): the cheapest buyable size's price (a range as an `AggregateOffer`), in stock by `availabilityOf`, in the store's currency, and no offer when prices are hidden; it once priced from `base_price`, read a `product.original_price` that does not exist, said in stock for every product and BHD for every store. `tests/product-feed.test.ts`, `tests/product-feed-handler.test.ts`, `tests/product-page-google-data.test.tsx`, `tests/shopping-feed-card.test.tsx`.
  - A product's price on a card and whether it is on sale: **one rule, `src/lib/product-price.ts`** (`cardPrice`, `productOnSale`), read by both cards, the home sale rail, the sale collection (`?cat=sale` and the offers query), the recommendation rails and both search lists. Prices live on variants (`products` has no `original_price`: the new-look card read it and never showed a sale). Only what a shopper can buy now counts (a variant with ready pieces, or any variant of a product made to order while making is open, or a service), so a sold-out size neither sets "from" nor puts a product on sale; the struck price is the cheapest buyable variant's own (`from 23, was 30, -23%`). The badge follows the store's and the product's switches (`global_sale_badges_enabled`, `show_sale_badge`). `tests/product-price.test.ts`. On the home page a product shows in one rail only, claimed sale, best sellers, trending, newest, among the rails drawn (`homeMerchandising`'s `shown`); the "All products" grid stays whole (`tests/home-products.test.ts`).
  - The inventory list: `useInventoryList` (`hooks/use-inventory-list.ts`) owns what the list shows and works each product's figures out once (`productFiguresFrom`). The view (tab, search, category, issue, sort, page) lives in the address (`lib/list-view.ts`, written with `replaceUrlQuietly`; the route's `validateSearch` keeps its parameters). **One attention rule**: `productAttentionReasons` (`lib/attention.ts`) is the "Needs attention" tab, its count, the marks on a row (`AttentionMarks`, desktop and phone) and the issue filter; never work an issue out on a surface. Totals above the list: `stockTotals` (`lib/stock-totals.ts`, `StockOverviewStrip`; cost only for `canViewFinancials`).
  - Low stock is the store's number: `business_settings.low_stock_threshold` (5 by default, 0 turns the warning off; migration `20261012180000`), set in the inventory page's summary by a member who may change settings (`saveLowStockLevel`; registry owner `route:inventory`). Read it with `lowStockLevel` (`src/lib/inventory-health.ts`) or `useLowStockLevel` and pass it to `productAvailability` / `isLowStock`: the list, the dashboard, the export, the products report and the phone alert (`enqueue_mobile_low_stock_push`, silent for a made-to-order piece and a service) all do. **Never write the number 5 on a new surface** (`tests/low-stock-level-migration.test.ts`, `tests/inventory-upgrades.test.tsx`).
  - A change to a variant's stock is made once and says why: `StockChangeControl` opens a dialog (new stock received, count correction, damaged or lost) and `planStockChange` (`lib/stock-change.ts`) turns it into one `rpc_adjust_variant_stock` call. An arrival and a loss are sent as a difference (an order placed meanwhile is not undone), a count sets the number; the reason and note are what the stock history shows. A row must not send a request per press of a button.
  - Auto-hide at zero stock: the trigger `sync_product_active_on_variant_stock` hides a product when all its variants reach zero stock and shows it again when stock returns (only if it hid it: `auto_deactivated_out_of_stock`). A made-to-order product (`is_made_to_order`) and a service are left alone (migration `20261010100000`, tested in a real Postgres by `tests/made-to-order-not-auto-hidden-migration.test.ts`): ready stock says nothing about whether they can be bought.
  - Availability (ready stock vs made to order): **one rule, `src/lib/product-availability.ts`** (`productAvailability`, `availabilityOf`, `isSoldFromStock`, `availabilityBadge`). A product sold from stock is out, low or available by its ready pieces; a made-to-order piece is "made to order" whatever its ready stock, and a service has nothing to count. The inventory tabs and "needs attention" (`productStockStatus` in `features/inventory/lib/product-list.ts`), the list badge on desktop and mobile (`StockLevelBadge`), the dashboard stock figures, the order editor product search, the product export (`features/import-export/lib/export-stock-status.ts`) and the storefront (`hasAvailableStock`) all read it; never decide "out of stock" from stock alone on a new surface.
  - Made-to-order limit: `products.made_to_order_available` (null: no limit; N: pieces that can still be made; migration `20261010110000`). A total: it goes down when an order with a made-to-order line (`order_items.location = 'custom'`) is placed and comes back only when that order is released (cancelled, refunded, voided, failed), by the order engine itself (`order_inventory_transition` calls `order_made_to_order_transition`; an order asking for more than is left is refused with `MADE_TO_ORDER_SOLD_OUT:<product>`). Orders placed before the limit was set do not count (`made_to_order_limit_set_at`). The number is changed only by the engine and by `set_made_to_order_limit` (staff; `setMadeToOrderLimit` in `src/lib/data/catalog/mutations.ts`, the editor field `MadeToOrderLimitField`): a direct UPDATE is refused, so **never put the column in a product form payload**. Every change is in `made_to_order_movements`; what an order holds is in `order_made_to_order_allocations`. The storefront reads the number through the product selects and `get_storefront_page_data`; `madeToOrderLimit` in `src/lib/product-availability.ts` says when the limit is used up (the product page then sells ready sizes only). Tested in a real Postgres through the engine by `tests/made-to-order-limit-migration.test.ts`.
  - How a product is sold, in the editor: one question in the basics tab, `SaleModeSection` ("From ready stock" or "Made to order" in the store's own word; "both" is not a stored state, it is a made-to-order product that also has ready sizes in its options table). Under it `MadeToOrderPanel` holds everything about making to order: the limit (`MadeToOrderLimitField`; a new product types its first limit, set by `use-save-product` after it is created), a pause and the record of changes (`madeToOrderQueries.history`, lines by `madeToOrderMovementLine` in `features/inventory/lib/sale-mode.ts`). Pause: `products.made_to_order_paused_at` (migration `20261010120000`), set only by `set_made_to_order_paused` (`setMadeToOrderPaused`); while paused the storefront closes made to order (`madeToOrderLimit().closed`) and the order engine refuses a shopper's order placed since the pause (`MADE_TO_ORDER_PAUSED`); earlier orders and staff orders go on, and the limit keeps its number (`tests/made-to-order-pause-migration.test.ts`). The placeholder "Standard" variant of a made-to-order product with no ready stock shows `MadeToOrderOnlyNote` instead of stock steppers.
  - Stored pictures: a file under `brands/<brand>/product/` can be pointed at from a product's main picture, its gallery (a picture or a video's poster) and a variant's own picture, and a duplicated product shares its original's files. **A file is deleted only when nothing points at it**: `deleteR2Object` (`src/lib/r2-upload.functions.ts`) asks `productPictureInUse` (`src/lib/product-picture-use.ts`) first and keeps a file that is in use, so a caller (the editor's `commitMedia`, deleting a product) only has to say it stopped using it. Removing a gallery picture clears the variants that were given it (`clearVariantPictures`) before the file goes, and a new product's first variant has no picture of its own (`defaultVariantValues`): a variant with none shows the product's. A variant that deliberately points at a gallery picture is how the product page jumps to that picture when the variant is chosen, so never clear those in bulk (`tests/product-pictures.test.tsx`).
  - Stock, its ledger and partners (incubators): a variant's stock is `stock_main` (the store) and `stock_incubator` (the total at partners), and **every change goes through the ledger** `apply_inventory_movement` (`inventory_movements`), which no browser can call: it is reached through functions that check their own caller (the order engine, the partner functions, `rpc_adjust_variant_stock` for a member of staff with `manage_inventory`). The nightly `reconcile_inventory` treats the ledger as the authority and resets a stock column that disagrees with it, so stock that never reached the ledger is lost the next night: a new variant's opening stock is written to it by a trigger (`trg_product_variants_opening_ledger`) and always starts in the store. Pieces at partners are also counted per partner (`incubator_inventory.quantity`), and the two are kept equal: the total moves only with a partner (`transfer_stock_to_incubator`, `return_stock_from_incubator`, `record_incubator_sale`, `reverse_incubator_sale`) or with an order, never by hand (`PARTNER_STOCK_MOVES_WITH_ITS_PARTNER`), so **the inventory screens show a partner quantity and never take one** (`partnerStockHint`). The storefront sells store plus partner stock; when the store's own runs out an order takes a piece from a partner (the one holding most first): `order_incubator_sync`, called by the ledger, lowers that partner's count, records it in `order_incubator_allocations` and in the partner's movements, and gives it back if the order is released. Staff read it as "Collect from a partner" on the order and in the packing dialog (`PartnerPickupNotice`) and as "Reserved by store orders" on the partner's page (`PartnerStockNotices`, which also warns when a total and its partners disagree); pure rules in `src/features/incubators/lib/partner-stock.ts`. Migration `20261012160000`, run in a real Postgres with the real engine, transfer, return and reconciliation by `tests/partner-stock-migration.test.ts`. **A shopper can collect at a partner's shop** (migration `20261014130000`): a partner takes pickups only when the store says so (`incubators.pickup_enabled`, with the address, map link, notes and `transfer_days`, set in the partner's form, `PickupFields`); the checkout asks `storefront_pickup_partners` (`checkoutQueries.pickupPartners`, the cart from `pickupCartItems`), which offers the partners that hold every ready piece (none with a made-to-order piece) without telling a visitor any quantity, and says when a branch pickup waits for pieces from a partner (`branchPickupNote`, under the branch in `PickupBranchCard`); when a partner holds the whole cart and the store's own stock does not cover it, no branch is offered and the partner is chosen (`pickupBranchesOffered`: a branch the piece was never at was offered, found on Pura's checkout); the order sends `pickup_partner_id` in `p_customer`, and `place_storefront_order` (the live one with one statement added, `tests/partner-pickup-builder-migration.test.ts`) calls `assign_order_pickup_partner`, which names the partner (`orders.pickup_incubator_id`), takes the ready pieces from it (a piece held at another partner moves to it) or refuses with `PICKUP_PARTNER_UNAVAILABLE`; `order_incubator_sync` prefers the order's pickup partner. Partners do not use the system: the order's `PartnerPickupNotice` says the customer collects there and offers a WhatsApp message a person sends (`partnerPickupMessage`). `tests/partner-pickup-migration.test.ts`, `tests/partner-pickup-checkout.test.tsx`.

## 6. Core Domain Concepts

1. **Store Verticals & Addon Packs** (`src/lib/verticals/registry.ts`, `src/lib/store-profile.ts`, `src/lib/addons/addon-registry.ts`): Stores belong to business verticals (`business_settings.store_vertical`: `fashion` › `abayas`, `beauty` › `fragrance`, `food` › `coffee`, `jewelry`, `gifts`, `print`, `services`, etc.; `electronics` is legacy: valid, not offered). The vertical registry is the single source for each vertical's name, summary, icon, parent, status, modules and starter pack; add a vertical there (tests/vertical-registry.test.ts checks every per-vertical table covers it). A child vertical (abayas under fashion, coffee under food) gets its parent's add-ons: match add-on `activities` with `verticalFits`, never `activities.includes(vertical)`, and list verticals in pickers with `pickerVerticals`. Verticals determine starter packs, default design presets, and category templates. The vertical is set by the platform: only a super admin (or trusted server code) can change it, enforced by the `guard_store_vertical` trigger; brand staff manage their add-ons. A change goes through the super admin's change dialog (`src/components/settings/VerticalChangeDialog.tsx`): the pure planner `src/lib/verticals/vertical-change.ts` previews it, then `changeBrandVertical` installs the add-ons the new vertical needs and the `apply_brand_vertical_change` RPC applies the rest in one transaction and records it in `brand_vertical_changes` with a reason. Never write `store_vertical` from a settings form. The planner also lists what a change leaves behind (`src/lib/verticals/vertical-leftovers.ts`: hand-set module overrides, goods left in a services store, open orders and bookings, incubators, returns, delivery settings; nothing is deleted). Admin screens are gated by module, never by vertical name, and data stays reachable while it exists; the rules, what was fixed and what is still to do are in [`docs/vertical-fit-audit.md`](./docs/vertical-fit-audit.md).
2. **Dynamic Variant Option Axes** (`src/lib/variant-axes.ts`): Variants store options in generic columns (`size`, `color`, `fabric`, `option_four`, `option_five`) whose meaning depends on the store (a roastery keeps the roast level in `color`). **Never label or render an option by its column name**: resolve labels and swatch-vs-chip rendering with `useVariantAxes` / `describeVariantAxes`, which combine the store vertical, installed addon packs and per-product label overrides.
3. **Hero Media Pipeline** (`src/lib/hero-media.ts`, `docs/media-video-pipeline.md`): Media items can be image or video. Videos are transcoded in-browser using WebCodecs + `mediabunny` into faststart MP4s. Resolvers choose optimal dimensions and crop focal points.
4. **Store Vocabulary** (`src/lib/store-vocabulary.ts`): Terminology adapts per vertical (e.g. "Abayas" vs "Products", "Tailoring" vs "Customization").
5. **Storefront Modes** (`src/lib/storefront-mode.ts`): Brands operate as a full shop with checkout (`shop`) or as a catalog (`catalog`): products shown with or without prices (`catalog_show_prices`) and a WhatsApp inquiry instead of checkout.

## 7. Architecture & Coding Rules

- **Vanilla Core Isolation**: Core files (`src/routes`, `src/components`, `src/lib`) **must never import from `@/addons/*` directly**. Enforced by ESLint restricted imports. Addons mount via `<AddonSlot />` or `@/lib/addons/*` bridge data.
- **Design Tokens**: Never hardcode hex colors or arbitrary pixel radii. Use semantic tokens (`bg-primary`, `text-muted-foreground`, `border-border`). Follow [`.agents/rules/AGENTS.md`](./.agents/rules/AGENTS.md).
- **RTL & Bilingual**: All UI components must support Arabic (RTL) and English (LTR). Use logical margins/padding or direction-aware flex layouts.
- **Every control has a name, in the reader's language**: a field is named by its label (`htmlFor` and `id`; `useId` when a card repeats, as an order's lines do) or by `aria-label`, never by its placeholder alone (it is gone once something is typed); a button that shows only an icon, a switch and a slider take an `aria-label` that says what they act on ("Delete column 3", "EID10 active"). The admin's list searches, the size guide studio (`studioNames`), a category's delete, a discount's switch, the content studio's sliders and an order line's fields had none (`tests/admin-accessible-names.test.tsx`).
- **A store's money is written in the store's currency**: `business_settings.currency`. On an admin screen read it with `useStoreCurrency(brandId)` (`src/hooks/use-store-currency.ts`) and pass it to `formatMoney`; a label or a field's tag that names the currency ("Price (BHD)") uses `useMoneyLabel(lang)` or the pure `currencyLabel(currency, lang)` (`src/lib/currency-label.ts`: the code in English, the short form Arabic readers know in Arabic). An amount that belongs to an order or a return is written in that order's own currency. Never write `"BHD"` or `د.ب` on a store's screen: the accounting tabs, the returns dialogs, a customer's page and some twenty-five labels once did (`tests/store-currency.test.tsx`). The platform's own prices (subscriptions, add-ons) are in BHD by design. **Every `formatMoney` call says both the currency and the reader's language** (`formatMoney(amount, currency, lang)`): without the language it writes English ("BHD 0.000") on an Arabic page, without the currency it writes BHD in every store (94 admin calls and a printed label did); `tests/design-system-guardrails.test.ts` fails on a call missing either, except the invoice message, `delivery-info` (whose `formatMoney` is a parameter) and the shelf label. Words a shared component writes on its own (a dialog's or a sheet's close button, the toasts' region) follow the page's language, `pageLanguage()` / `closeLabel()` in `src/lib/page-language.ts`. Screens say "cost of goods" and "running costs" (تكلفة البضاعة، المصاريف التشغيلية), never COGS or OpEx.
- **Asking before a step that cannot be undone** is `await confirmDialog({ title, destructive })` (`src/components/ui/confirm-dialog.tsx`, drawn by the one `ConfirmDialogHost` in `__root.tsx`): never `window.confirm` or `alert`, which look like a website, ignore the theme and may not show in the phone app's web view (`tests/design-system-guardrails.test.ts`). **The platform's address is `src/lib/platform-host.ts`** (`storeAddress`, `adminAddress`): the onboarding wizard once handed new merchants `boutq.app` links, a domain that does not answer. **A product is never filed under an automatic collection** (`assignableCategories`, `smartKindOf` in `src/lib/smart-categories.ts`).
- **A count is written by `countOf(n, noun, lang)` / `arNoun(n, noun)`** (`src/lib/arabic-count.ts`, `AR_NOUNS`: one, two, three to ten, eleven and over, and the bare noun for zero and the hundreds): "طلب واحد", "طلبان", "7 طلبات", "11 طلبًا". The admin wrote the number before one form whatever it was ("6 عملية بيع", "1 مهام معلّقة", "7 طلب"); a sentence whose words would have to agree with the count puts the count last ("تحتاج إجراءً فورياً: 6 طلبات"). `tests/design-system-guardrails.test.ts` fails on a number glued to the common nouns.
- **A period of days is sent as moments**: a screen's period is whole days (`YYYY-MM-DD`) on the reader's own clock, and a row's time (`created_at`) is a moment. A bare day sent to the database is read at midnight UTC, so in Bahrain an order placed between midnight and 03:00 on the 1st fell in the month before (the expenses page's cost of goods did this). Turn the days into bounds with `localDayRange` (`src/lib/day-range.ts`: from the first day's midnight, to before the midnight after the last) and compare with `gte` / `lt`; the report functions do the same with moments and the reader's time zone (`p_tz`), so the two agree. A column that is itself a day (`expense_date`, `event_date`) is compared as a day (`tests/day-range.test.ts`).
- **Shared Resolvers Over Surface-Specific Hacks**: Never duplicate resolution logic in a route; place canonical logic in `src/lib/` (e.g., `resolveHeroMedia`, `calculateStock`).
- **A list is read to its end, or says how many rows it wants**: the API answers a list with at most its row limit (1,000 rows) and does not say that it stopped, so a store's 1,001st variant, customer or order was simply not there: a total was short, a cost read as zero, an import made duplicates, an export lost its tail. A reader whose caller treats the result as the whole list goes through `readAll` (`src/lib/data/read-all.ts`): its page function asks for one range in a fixed order that ends on a unique column (`.order("id")`) with `{ count: "exact" }`; a list that fits costs one request, as before, and a longer one is read whole (the count says how much is left, and the rest is asked for at once). Any other list read says its bound: `.limit()`, `.range()`, one row, or a list of ids. The ratchet counts list reads with neither (`unboundedListReads` in `scripts/maintainability-metrics.mjs`, `tests/maintainability-ratchet.test.ts`): what is left is settings-sized tables and one parent's rows, and the number only goes down. The lists a screen holds whole (the inventory's products and variants, the orders list, customers) are filtered and paged in the browser on the complete list: that is right for a boutique's thousands of rows; moving a list's filters and counts into SQL would need a second copy of its rules (`tests/read-all.test.ts`).
- **Data Access Layer** (`src/lib/data/`, see its README): reads and writes live in one module per domain with `selects.ts` (column lists), `keys.ts` (query-key factories), `queries.ts` (fetchers + `queryOptions`) and `types.ts`. Screens call `useQuery(xxxQueries.foo(...))` and never build keys or queries by hand. Migrated so far: the public storefront catalog (`storefront/`); admin orders reads + writes (`orders/`, incl. finance, COGS and reconciliation views); `business-settings/`; `expenses/`; admin catalog reads + writes (`catalog/`: products, variants, stock, BOM, packaging, add-ons); customers and saved addresses, admin and storefront (`customers/`); settings writes (`business-settings/`, `brands/`). ESLint `no-restricted-syntax` enforces them on the storefront routes and slices, and on the orders, dashboard, accounting, expenses, inventory, customers and settings screens (no direct `from(...)` for those tables, no hand-built keys). Also `returns/` and `reporting/` for the dashboard, admin `categories/`, `loyalty/`, `promo-codes/`, `incubators/`, `message-templates/` and `profiles/` (the route guards' caller profile). `returns/` covers the admin returns screens too; `push/` the push centre; `notification-recipients/` the admin alert recipients; `media-optimizer/` the super admin video re-optimizer; `abandoned-carts/` the admin abandoned-carts screen; `integrations/` the integrations screen; `super-admin/` the super admin's platform screens; `import-export/` the import and export history; `checkout/` the storefront checkout's calls; `addons/` the addon data core screens read; `activity-logs/` the activity log; `system-settings/` the platform settings row; `branches/` a brand's branches (admin and checkout pickup); `reviews/` order reviews (admin and public); `brands/` the brand lookups (admin route guard, switcher, onboarding, storefront host); `reporting/` the Reports pages (one overview cache shared with the dashboard). `accounting/` covers the expenses page's cash accounts, vendors and purchase orders tabs. `content-drafts/` holds the content studio's saved drafts. `bookings/` holds a services store's booking rules, bookings, blocked days and public availability (writes go through the booking functions; pure rules in `src/lib/bookings/rules.ts`). `verticals/` holds a store's vertical change history and the change preview. Session reads and sign-out go through `@/lib/auth/session` (`getCurrentUser`, `getCurrentSession`, `getAccessToken`, `signOut`; route guards use `ensureSessionUser`). **A sign-out ends this device's session only** (`signOut`, `scope: "local"`; Supabase's default ended every device's, the phone app's included); `signOutEverywhere` is the person's own button (`SignOutEverywhere` in Settings → Account → Security). **"Keep me logged in" is where the session is kept**, never a sign-out on load: the client's storage is `rememberingStorage` (`src/lib/session-persistence.ts`), the browser's lasting storage unless the person unticked the box (`applyRememberMe(false)`), then its session storage, which the browser empties when it closes; a sign-in with no box stays signed in (`tests/session-persistence.test.ts`). The sign-in flows (password, passkey, Google, storefront sign-up and membership, recovery, first login, passkey management) go through `@/lib/auth/sign-in`, which returns Supabase's results unchanged. ESLint forbids `supabase.auth.*` in routes, components and features. Still direct: the server routes (`src/routes/api.*`, the manifest route), and the order editor's realtime subscription. Method: [`.agents/skills/data-layer-migration`](./.agents/skills/data-layer-migration/SKILL.md); status and next steps: [`docs/agent-handoff.md`](./docs/agent-handoff.md).

## 8. Database & Security Rules

- **Production Database**: Linked to remote Supabase. Treat as **read-only** by default (`npx supabase db query --linked "<select>"` is fine). Never execute `db reset`, `db push`, `migration repair`, or unvetted DDL; the owner applies migrations (`npx supabase db push --linked`) after reviewing a `--dry-run`.
- **Who may open a page of a store's admin**: one table, `PAGE_ACCESS` in `src/lib/page-access.ts` (the page is the first part of the address after the store; a rule is a permission a member of staff needs, or admins only), held by one guard in the admin layout's `beforeLoad` (`admin.b.$slug.route.tsx`: `mayOpenPage`; a courier has `orders` and nothing else; whoever may not open a page is sent to one they can, `homePageOf`). Five pages once carried their own copies of the check, with small differences, and the others had none: the menu hid a page and its address still opened it. **A new page gets a row in the table, not a guard of its own**; the menu item carries the same rule. `tests/page-access.test.ts` keeps the table, the route files and the menu equal, and `tests/super-admin-platform-navigation.test.tsx` runs the guard. This decides what a person is shown; what data comes back is the database's rules (next line). The platform's owner is known in the app by one constant, `SUPER_ADMIN_EMAIL` (`src/lib/profile-context.tsx`), and in the database by role.
- **The admin's menu is one definition** (`src/config/admin-navigation.ts`): six workspaces as a boutique owner names them (Home, Orders, Products, Customers & marketing, Money, Store), each page in exactly one, the daily pages in view and the rare ones (`rare`) folded under "More tools" (`OsNavMore`). The sidebar, the phone's dock and menu sheet, the workspace tabs, the desktop rail, the tools directory and the command palette all read it through `adminNavGroups`, `dockWorkspaces`, `workspaceTabs` and `isNavItemActive` (a page or its own pages, never one that only starts alike). The phone's dock once lit its tabs from its own lists of addresses (five pages were missing) and the palette listed its own pages with no permission rule. **A new page gets one item there** (with its `PAGE_ACCESS` rule), nothing else; `tests/admin-navigation-architecture.test.ts` holds every page in exactly one workspace.
- **Row Level Security (RLS)**: Every multi-tenant table enforces RLS. Security functions live in Postgres (`can_access_brand`, `is_brand_owner`, `is_super_admin`). Always scope queries by `brand_id`.
- **Two-factor sign-in for staff** (migration `20261027150000`, `tests/staff-two-factor-migration.test.ts`; the owner's decision of 2026-10-27: optional, each member turns it on): an authenticator-app code (Supabase Auth TOTP) after a password or a passkey. **The database holds it where every staff permission is decided**: `can_access_brand`, `has_permission`, `is_admin` and `is_super_admin` each end with `staff_session_verified()` (server-only), true for a session that gave its code (`aal2`) and for a member without two-factor, so a browser that skips the code screen gets nothing of a store and nobody without it notices anything. A new permission function must end with the same condition. The admin opens behind `TwoFactorGate` (in the `_authenticated` layout); a member turns it on or off in Settings → Account → Security (`TwoFactorSettings`); the calls are `src/lib/auth/mfa.ts`; the Team page marks who has it on (`brand_staff_two_factor`, admins only). `tests/staff-two-factor-screens.test.tsx`.
- **Function grants (RPCs)**: a SECURITY DEFINER function is callable by the browser unless its grant is removed (Supabase grants EXECUTE to `anon`, `authenticated` and `service_role` on every new function), so a function that only the server calls (secrets, payment state, quotas) must be revoked from `anon` and `authenticated` in the migration that creates it, and a function the browser does call must check the caller inside. Never write the check as `IF auth.uid() IS NOT NULL AND NOT can_access_brand(...)`: it is skipped for an anonymous caller. The first clean-up is `20261007110000_revoke_browser_access_to_server_functions.sql` (tested in a real Postgres by `tests/revoke-browser-access-migration.test.ts`); `20261007140000_loyalty_and_coupons_server_side.sql` moved loyalty award/redeem to the server: the browser asks `src/lib/loyalty-checkout.functions.ts` (`redeemLoyaltyForOrder`, `awardLoyaltyForOrder`), which checks the order is the signed-in shopper's and calls the database as the service role. Redeeming points lowers the order's own total in one transaction (`redeem_loyalty_points_for_order`, migration `20261007150000`: discount and total like a promo code, `orders.loyalty_points_redeemed` / `loyalty_discount`); before that the points discount was only drawn in the checkout summary.
- **Guard**: `supabase/function-grants.json` lists every SECURITY DEFINER function a browser (`anon` or `authenticated`) can call, with the reason; `npm run db:function-grants:check` (and the CI job "Supabase Linked Migration Drift Check") reads the live database and fails on one that is not listed, so a new function that only the server calls must be revoked in its migration (apply the migration first, as always) and one a browser calls must check the caller inside and be listed. `tests/function-grants-guard.test.ts` keeps the list honest and bans the fail-open check from new migrations. The same check fails on a read policy written `TO anon` that calls a function a visitor cannot execute (e.g. `USING (is_active OR can_access_brand(brand_id))` made every visitor read of `advance_payment_rules`, the FAQ and the gallery fail with "permission denied for function"; migration `20261009130000`): keep a visitor policy to plain columns and give staff their own policy `TO authenticated` (tested in a real Postgres by `tests/visitor-read-policies-migration.test.ts`).
- **A public server function is careful with what it pays for and what it stores**: `translateOptionTerms` (`src/lib/translate-options.functions.ts`) is called from a shopper's page, so anyone can call it. It looks only at short words (`translatableTerms`), sends the paid model only the words a store really sells under (`catalog_option_values`, service role only: an option value of a variant, or a product's fabric or occasion), keeps of the answer only a short translation of a word that was asked (`acceptedTranslations`), and does not store what the built-in lexicon already answers. The shared `translation_cache` is written by the server only: the policies that let any signed-in account, a shopper's included, rewrite a row are gone (migration `20261013120000`, `tests/translate-option-terms.test.ts`). A new server function with no auth middleware needs the same thought: what can a stranger make it spend, and what can they make it keep.
- **What a visitor may write**: an insert policy `WITH CHECK (true)` lets anyone write any row, of any size, as often as they like. A table only the server writes has no browser policy and no browser INSERT grant (`tenant_requests`: the form saves through `onboarding.functions.ts`, which checks and rate-limits). A table a visitor does write (`shared_carts`) gives the browser INSERT on the columns a visitor sets and nothing else (the expiry is the table's default), holds CHECK constraints for the row's shape and size, is read through a function, and has a nightly job for what expires (`delete_expired_shared_carts`, pg_cron `shared_carts_cleanup_nightly`). Migration `20261013140000`, tested in a real Postgres as a visitor by `tests/public-writes-bounded-migration.test.ts`. The same care for a server function anyone can call: one that fetches an address for its caller (`getInvoiceAssetDataUrl`) fetches only from the platform's own hosts, follows no redirect and stops at a byte limit (`src/lib/invoice-asset-rules.ts`, `tests/invoice-asset-rules.test.ts`).
- **Costs are for staff who may see the store's finances**: a product's and a variant's costs live in `product_costs` / `variant_costs`, read and written only by `can_view_brand_costs(brand)` (the store's staff holding `view_financials`, like the expenses, suppliers and purchase orders; migrations `20261007170000`, `20261008100000` and `20261013150000`). A member of staff without the permission reads no cost, so their screens show no cost field (`ProductCostField`, the variant rows, the packaging dialog's direct cost) and, because a form that cannot read a cost holds zero, **the database keeps the cost columns as they are when such a person saves** (`trg_products_keep_costs`, `trg_product_variants_keep_cost`: the rest of the save goes through; a new product starts with no cost and a new variant takes its product's). The server and the database's own functions are not held back. Run in a real Postgres as an owner, a stock clerk and the server by `tests/costs-financial-permission-migration.test.ts`; screens in `tests/cost-fields-permission.test.tsx`. Still open to any office staff, on purpose for now: an order line's cost snapshot (`order_items.unit_cost`) and the packaging materials' unit costs (an inventory matter). The old cost columns on `products` / `product_variants` stay for writes (triggers copy them across) but `authenticated` and `anon` cannot SELECT them, so **never `select("*")` on those two tables**: the admin reads named columns (`src/lib/data/catalog/selects.ts`, kept equal to the generated types by `tests/catalog-admin-columns.test.ts`) and merges costs in with `src/lib/data/catalog/costs.ts`. A column added to either table needs `GRANT SELECT (col) ON public.<table> TO authenticated;` in its migration; `npm run db:catalog-columns:check` (CI) fails otherwise.
- **Additive Migrations**: Schema changes must be backward-compatible, sequential SQL scripts in `supabase/migrations/`. Check with `npm run db:migrations:check`. Local and production history match (zero drift); CI fails a PR whose migration is not applied yet, so apply (owner) → verify → regenerate types → open the PR.

## 9. Maintainability Ratchets & Quality Gates

Maintained in [`tests/maintainability-ratchet.test.ts`](./tests/maintainability-ratchet.test.ts); current numbers in [`docs/maintainability.md`](./docs/maintainability.md):

- **Ceilings move only down**: `as any`, `: any`, `as never`, `@ts-ignore`, `eslint-disable`, direct Supabase calls, and brittle `readFileSync` test files are strictly capped. Increasing any count breaks CI.
- **Giant File Freeze**: Existing files $>1,000$ lines cannot grow. New files must stay under **600 lines**.
- **Behavior Testing**: Never test a feature by reading its source text. Call the pure function (extract it into `src/lib/` or the feature's `lib/` if needed) or render the component with its data layer mocked. Server functions and middleware run in tests through [`tests/helpers/server-fn.ts`](./tests/helpers/server-fn.ts) (a recording `createServerFn` and a fake Supabase client). `readFileSync` is left only for SQL / edge-function contracts and architecture guards; see [`docs/behaviour-tests.md`](./docs/behaviour-tests.md).
- **Pull Requests**: Fill in the checklist in [`.github/pull_request_template.md`](./.github/pull_request_template.md) (quality gate, ratchet, behaviour tests, data layer, RTL, screenshots, owner-applied migrations, bug backlog).

## 10. Known Pitfalls

- **Vitest Memory & Worker Timeouts**: Full test suite (`npx vitest run`) executes 1,000+ tests. Run specific files during development: `npx vitest run tests/<file>.test.ts`.
- **JSDOM Stubs**: Browser globals like `scrollIntoView`, `matchMedia`, and `window.open` are stubbed in [`tests/setup.ts`](./tests/setup.ts). Add mocks there if needed.
- **No Network in Unit Tests**: [`tests/setup.ts`](./tests/setup.ts) rejects every `fetch` and WebSocket, because the Supabase client points at production. Mock the data layer; `vi.mock` needs the relative path (`../src/lib/data/x`) as well as the `@/` alias, or the real module runs and its request is refused. CI has no Supabase environment (locally `.env` hides this): a test that lets real code build `@/integrations/supabase/client` passes locally and fails in CI, so mock it and try new tests with `.env` moved aside.
- **Windows vs POSIX Paths**: In scripts, always normalize backslashes (`path.replace(/\\/g, "/")`). Avoid unescaped `$slug` variables in PowerShell commands.
- **Content cut off at the side of a phone**: html, body and the page shells hide sideways overflow, so a block that grows wider than the screen is not scrolled to, it is cut off (the checkout lost the edge of every field when a product name was long), and `document.scrollWidth` says nothing. Three guards: (1) a grid with no columns of its own is one implicit `auto` column that cannot be narrower than its widest content, so `src/styles/layout-guards.css` sizes it `minmax(0, 1fr)` for every such grid; (2) in an arbitrary template write `minmax(0,1fr)`, never a bare `1fr` (`tests/design-system-guardrails.test.ts` fails on one); (3) the overflow audits open every storefront page and every admin screen (a store's and the platform's) at 320px and 390px, in Arabic and English, with long names and a word that cannot wrap, press each page's buttons to open its dialogs, drawers, menus and tabs, and measure the boxes (`tests/storefront-overflow-audit.spec.ts`, `tests/admin-overflow-audit.spec.ts`, rules in `tests/helpers/overflow.ts`). They take about half an hour, so they are **on demand, not part of the pull-request checks**: `npm run audit:overflow` (`-- --stores=zh,pura`, `-- --screens=orders,settings`, `-- --admin`, `-- --storefront`); run it after layout work on a page, and put a new admin screen in its list. A row of buttons needs `flex-wrap`; a native `<select>` is as wide as its longest option, so give it `max-w-full`.
- **Text cut short**: a name (a product, a customer, an order line, a store) is never cut to one line: `line-clamp-2 break-words`; in a product grid the card is a column whose price sits at its foot (`mt-auto`), so a row's prices line up whatever its names take, with no empty line kept under a short name (`ProductCard`, `ProductCardV2`). A name whose language may differ from the page's takes `dir="auto"` with `text-page-start` (`src/styles/layout-guards.css`), so an English name on an Arabic page is cut at its own end and still sits at the page's start edge. `truncate` is for secondary lines only, and whatever is still cut anywhere can be read in full: `TruncationReveal` (`src/components/ui/truncation-reveal.tsx`, mounted once in `__root.tsx`, rules in `src/lib/truncation.ts`) shows the whole text beside it on a rest of the mouse, a tap on plain text, a long press inside a link or a button, or keyboard focus; `data-no-reveal` opts an element out. `tests/design-system-guardrails.test.ts` fails on a product title cut to one line and caps the number of `truncate`s.
- **On a phone, a website gives itself away** (`src/styles/mobile-native.css`, guarded in `tests/design-system-guardrails.test.ts`): a field under 16px makes iOS zoom into the page, so on a touch screen a field sized smaller by its class is 16px (the admin's list searches were 12px); never `maximum-scale` or `user-scalable=no`. A `:hover` that moves something is for a mouse only, `@media (hover: hover) and (pointer: fine)` (Tailwind's `hover:` already is): a tap keeps `:hover` on. A fixed bar at the top or bottom pads itself with `env(safe-area-inset-*)` (the page is `viewport-fit=cover`). The status bar's colour is `theme-color`: the admin's bar in its theme (`src/lib/theme-color.ts`, set by `ThemeProvider`), a store's header colour on its pages. A sideways row of cards snaps (`snap-x snap-mandatory`, cards `snap-start`). A finger needs 44px: on a touch screen every control in the admin (its dialogs too) takes taps over an invisible box at least 44px each way, centred on it, without being redrawn (58 of the inventory's 68 controls were smaller); one placed over something else (`absolute`, `fixed`) or drawing its own `after:` is left out, and a row that scrolls sideways clips that box, so its tabs are 44px tall on touch (`pointer-coarse:min-h-11`, the workspace tabs). A field a finger opens is 44px tall on touch too (inputs, selects, a dropdown's trigger), and a button in the same row as a field takes its height, a square icon button staying square; a box with a fixed height around a field (a quantity stepper) is `pointer-coarse:h-auto`. A phone row of filters is one sideways row with whole labels (`OrdersScopeSwitcher`, `InventoryScopeSwitcher`); on a phone the orders that need action are told by their own filter tab, amber while it holds orders (`urgent` in `orderQueueTabs`), not by a banner under it (`UrgentOrdersBanner` is from `sm` up), a search's placeholder fits its field on a 375px phone (the keyboard hint `useShortcutHint` is left out on a touch screen), and the product editor is the whole screen on a phone. Coming back to the app reads nothing: Supabase reports `SIGNED_IN` on every return and `TOKEN_REFRESHED` hourly, and the profile is read again only for a new person or `USER_UPDATED`, keeping the object it holds when the answer is the same (`profileAuthAction`, `keepIfSame` in `src/lib/profile-refresh.ts`; `tests/admin-phone-polish.test.tsx`). Emulation in a desktop browser shows none of this; check on a phone.
- **Long text in a flex row**: a `truncate` element only truncates when every flex ancestor up to the box has `min-w-0` (a flex item's minimum width is its content's, so one URL or file name pushes the row past its box). `DialogContent`'s single column is `minmax(0,1fr)` for the same reason; give a row inside a card its own `min-w-0 flex-1`.
- **A push of a branch must not release it**: Cloudflare builds every pushed branch, and its build settings once released each of them (found 2026-10-13: code was live on push, hours before its pull request merged). The setting that decides is in the Cloudflare dashboard (the worker's Builds settings: the non-production branch deploy command must be `npx wrangler versions upload`); `npm run deploy` also releases only a build of `main` (`scripts/deploy-plan.mjs`, `tests/deploy-plan.test.ts`). Merging to `main` is the release. Never call `wrangler deploy` from a script or a workflow directly, and **check before relying on it**: after a branch push, `npx wrangler deployments list` must show no new deployment. Until that is true, treat a push as a release (see `docs/ci-cd.md`).
- **A scheduled run happens once**: Cloudflare starts the worker's scheduler, and since 2026-10-12 it has started every run twice a few seconds apart. `runScheduledTasks` claims its minute first (`claimScheduledRun` in `src/lib/observability.server.ts`, the database function `claim_scheduled_run`, migration `20261013180000`); a second start for the same schedule and minute does nothing. It runs anyway when the claim cannot be asked. `tests/scheduled-run-claim-migration.test.ts`.
- **Two tables joined two ways**: a select that brings a table in under another (`purchase_order_items(..., order_items(...))`) must name the link (`order_items!purchase_order_items_order_item_id_fkey(...)`) as soon as the two are joined by more than one foreign key, either way, or the API refuses the whole read (PGRST201). Adding a second link to a table (`released_order_item_id`, migration `20261021100000`) broke the supplier orders list in every store, which mocked screens could not see. `tests/postgrest-embed-ambiguity.test.ts` reads the links from the generated types and every select in the code: regenerate the types after a migration and it fails on a select left unnamed.
- **Generated Files**: **Never manually edit** `src/routeTree.gen.ts` (generated by TanStack Router) or `src/integrations/supabase/types.ts` (generated by Supabase CLI).
