# AGENTS.md — Boutq OS Architecture & Contributor Guide

Welcome! This document is the primary entry point for AI agents and human engineers working on Boutq OS (`bhpura-d219813a`). Every statement here is verified against the codebase as of September 2026.

---

## 1. What Boutq Is

Boutq is a multi-tenant e-commerce and brand operations platform for GCC boutique brands.

- **Tenants / Brands**: Each merchant owns a brand scoped by `brand_id` and unique `slug` (e.g. `/pura`).
- **Surfaces**:
  - **Storefront (`src/routes/$slug.*.tsx`)**: Public shopping experience. Supports bilingual (AR/EN), RTL-first layout, currency formatting, and two sales modes (`storefront_mode`: `shop` for direct checkout, `catalog` for a showcase with WhatsApp inquiries and optional prices).
  - **Admin Panel (`src/routes/_authenticated/admin.b.$slug.*.tsx`)**: Authenticated back-office for catalog, inventory, orders, marketing, expenses, team, and settings.
  - **Super Admin (`src/routes/_authenticated/admin.super.*.tsx`)**: Platform operations, tenant provisioning, system health, and billing plans.
- **Storefront Engine (V1 vs V2)**: Governed by `storefront_design_version` (1 or 2) in `business_settings`.
  - V1: Classic stable layout with 1:1 product cards.
  - V2: Premium agency-grade experience with 3:4 cards, cinematic hero (`HeroV2`), quick add, color swatches, and vertical design presets (`editorial`, `fresh`, `tech`). See [`docs/storefront-architecture.md`](./docs/storefront-architecture.md).

## 2. Tech Stack & Runtimes

- **Web**: React 19.2, TanStack Start (Vinxi / Vite), Tailwind CSS v4, Lucide icons, Radix UI primitives.
- **Mobile (`apps/boutq-os-mobile/`)**: React 19.1, React Native 0.81, Expo 54, React Navigation.
- **Runtime Host**: Cloudflare Workers (SSR + edge functions) with Cloudflare R2 object storage.
- **Backend & Database**: Supabase (PostgreSQL 15, RLS tenant isolation, Auth, Storage, Deno Edge Functions).

## 5. "Where Do I Change X?" (Quick Reference)

- **Products & Catalog**:
  - Admin management: `src/features/inventory/` (`components/` for the product list, product editor and variant table; `hooks/` for data and mutations; `lib/` for pure, unit-tested rules). The route `src/routes/_authenticated/admin.b.$slug.inventory.tsx` only loads data and picks the tab. Shared inventory UI: `src/components/inventory/`
  - Storefront product page: `src/routes/$slug.product.$id.tsx` (composition) + `src/features/product-page/` (option rules, pricing, cart line, gallery, pickers). Priced options (an add-on in `customization_options`, or a listed choice of a product's select field whose text names a price, "Silk lining (+ 5 BHD)") are priced by the database from the store's own data, never from the browser's price: `storefront_line_customizations` (migration `20261011100000`, service role only) feeds the order builder, which charges (price + options) x quantity and writes `order_items.customizations` / `customization_total`. `fieldPriceDelta` (`lib/variant-options.ts`) is its twin for the product page and cart: free text a shopper types never carries a price (`tests/priced-options-migration.test.ts` runs both against each other)
  - Cards & presentation: `src/components/storefront/product-card.tsx` (`ProductCard` / `ProductCardV2`)
  - The inventory list: `useInventoryList` (`hooks/use-inventory-list.ts`) owns what the list shows and works each product's figures out once (`productFiguresFrom`). The view (tab, search, category, issue, sort, page) lives in the address (`lib/list-view.ts`, written with `replaceUrlQuietly`; the route's `validateSearch` keeps its parameters). **One attention rule**: `productAttentionReasons` (`lib/attention.ts`) is the "Needs attention" tab, its count, the marks on a row (`AttentionMarks`, desktop and phone) and the issue filter; never work an issue out on a surface. Totals above the list: `stockTotals` (`lib/stock-totals.ts`, `StockOverviewStrip`; cost only for `canViewFinancials`).
  - Low stock is the store's number: `business_settings.low_stock_threshold` (5 by default, 0 turns the warning off; migration `20261012180000`), set in the inventory page's summary by a member who may change settings (`saveLowStockLevel`; registry owner `route:inventory`). Read it with `lowStockLevel` (`src/lib/inventory-health.ts`) or `useLowStockLevel` and pass it to `productAvailability` / `isLowStock`: the list, the dashboard, the export, the products report and the phone alert (`enqueue_mobile_low_stock_push`, silent for a made-to-order piece and a service) all do. **Never write the number 5 on a new surface** (`tests/low-stock-level-migration.test.ts`, `tests/inventory-upgrades.test.tsx`).
  - A change to a variant's stock is made once and says why: `StockChangeControl` opens a dialog (new stock received, count correction, damaged or lost) and `planStockChange` (`lib/stock-change.ts`) turns it into one `rpc_adjust_variant_stock` call. An arrival and a loss are sent as a difference (an order placed meanwhile is not undone), a count sets the number; the reason and note are what the stock history shows. A row must not send a request per press of a button.
  - Auto-hide at zero stock: the trigger `sync_product_active_on_variant_stock` hides a product when all its variants reach zero stock and shows it again when stock returns (only if it hid it: `auto_deactivated_out_of_stock`). A made-to-order product (`is_made_to_order`) and a service are left alone (migration `20261010100000`, tested in a real Postgres by `tests/made-to-order-not-auto-hidden-migration.test.ts`): ready stock says nothing about whether they can be bought.
  - Availability (ready stock vs made to order): **one rule, `src/lib/product-availability.ts`** (`productAvailability`, `availabilityOf`, `isSoldFromStock`, `availabilityBadge`). A product sold from stock is out, low or available by its ready pieces; a made-to-order piece is "made to order" whatever its ready stock, and a service has nothing to count. The inventory tabs and "needs attention" (`productStockStatus` in `features/inventory/lib/product-list.ts`), the list badge on desktop and mobile (`StockLevelBadge`), the dashboard stock figures, the order editor product search, the product export (`features/import-export/lib/export-stock-status.ts`) and the storefront (`hasAvailableStock`) all read it; never decide "out of stock" from stock alone on a new surface.
  - Made-to-order limit: `products.made_to_order_available` (null: no limit; N: pieces that can still be made; migration `20261010110000`). A total: it goes down when an order with a made-to-order line (`order_items.location = 'custom'`) is placed and comes back only when that order is released (cancelled, refunded, voided, failed), by the order engine itself (`order_inventory_transition` calls `order_made_to_order_transition`; an order asking for more than is left is refused with `MADE_TO_ORDER_SOLD_OUT:<product>`). Orders placed before the limit was set do not count (`made_to_order_limit_set_at`). The number is changed only by the engine and by `set_made_to_order_limit` (staff; `setMadeToOrderLimit` in `src/lib/data/catalog/mutations.ts`, the editor field `MadeToOrderLimitField`): a direct UPDATE is refused, so **never put the column in a product form payload**. Every change is in `made_to_order_movements`; what an order holds is in `order_made_to_order_allocations`. The storefront reads the number through the product selects and `get_storefront_page_data`; `madeToOrderLimit` in `src/lib/product-availability.ts` says when the limit is used up (the product page then sells ready sizes only). Tested in a real Postgres through the engine by `tests/made-to-order-limit-migration.test.ts`.
  - How a product is sold, in the editor: one question in the basics tab, `SaleModeSection` ("From ready stock" or "Made to order" in the store's own word; "both" is not a stored state, it is a made-to-order product that also has ready sizes in its options table). Under it `MadeToOrderPanel` holds everything about making to order: the limit (`MadeToOrderLimitField`; a new product types its first limit, set by `use-save-product` after it is created), a pause and the record of changes (`madeToOrderQueries.history`, lines by `madeToOrderMovementLine` in `features/inventory/lib/sale-mode.ts`). Pause: `products.made_to_order_paused_at` (migration `20261010120000`), set only by `set_made_to_order_paused` (`setMadeToOrderPaused`); while paused the storefront closes made to order (`madeToOrderLimit().closed`) and the order engine refuses a shopper's order placed since the pause (`MADE_TO_ORDER_PAUSED`); earlier orders and staff orders go on, and the limit keeps its number (`tests/made-to-order-pause-migration.test.ts`). The placeholder "Standard" variant of a made-to-order product with no ready stock shows `MadeToOrderOnlyNote` instead of stock steppers.
  - Stored pictures: a file under `brands/<brand>/product/` can be pointed at from a product's main picture, its gallery (a picture or a video's poster) and a variant's own picture, and a duplicated product shares its original's files. **A file is deleted only when nothing points at it**: `deleteR2Object` (`src/lib/r2-upload.functions.ts`) asks `productPictureInUse` (`src/lib/product-picture-use.ts`) first and keeps a file that is in use, so a caller (the editor's `commitMedia`, deleting a product) only has to say it stopped using it. Removing a gallery picture clears the variants that were given it (`clearVariantPictures`) before the file goes, and a new product's first variant has no picture of its own (`defaultVariantValues`): a variant with none shows the product's. A variant that deliberately points at a gallery picture is how the product page jumps to that picture when the variant is chosen, so never clear those in bulk (`tests/product-pictures.test.tsx`).
  - Stock, its ledger and partners (incubators): a variant's stock is `stock_main` (the store) and `stock_incubator` (the total at partners), and **every change goes through the ledger** `apply_inventory_movement` (`inventory_movements`), which no browser can call: it is reached through functions that check their own caller (the order engine, the partner functions, `rpc_adjust_variant_stock` for a member of staff with `manage_inventory`). The nightly `reconcile_inventory` treats the ledger as the authority and resets a stock column that disagrees with it, so stock that never reached the ledger is lost the next night: a new variant's opening stock is written to it by a trigger (`trg_product_variants_opening_ledger`) and always starts in the store. Pieces at partners are also counted per partner (`incubator_inventory.quantity`), and the two are kept equal: the total moves only with a partner (`transfer_stock_to_incubator`, `return_stock_from_incubator`, `record_incubator_sale`, `reverse_incubator_sale`) or with an order, never by hand (`PARTNER_STOCK_MOVES_WITH_ITS_PARTNER`), so **the inventory screens show a partner quantity and never take one** (`partnerStockHint`). The storefront sells store plus partner stock; when the store's own runs out an order takes a piece from a partner (the one holding most first): `order_incubator_sync`, called by the ledger, lowers that partner's count, records it in `order_incubator_allocations` and in the partner's movements, and gives it back if the order is released. Staff read it as "Collect from a partner" on the order and in the packing dialog (`PartnerPickupNotice`) and as "Reserved by store orders" on the partner's page (`PartnerStockNotices`, which also warns when a total and its partners disagree); pure rules in `src/features/incubators/lib/partner-stock.ts`. Migration `20261012160000`, run in a real Postgres with the real engine, transfer, return and reconciliation by `tests/partner-stock-migration.test.ts`.
  - Incubators (consignment partners) page: `src/features/incubators/` (the route `admin.b.$slug.incubators.tsx` only guards and mounts `IncubatorsPage`). `hooks/use-incubators-page.ts` holds the queries, the open partner and the actions; `components/` draw it: the partner picker and figures (`IncubatorOverview`), the stock (`IncubatorStockTab`: a table on a wide screen, a card per piece on a phone), the sales with everything that was agreed, the payments with the sales each settled, and the history (`IncubatorLedgerTabs`), the forms and the reverse-sale confirmation (`IncubatorDialogs`), and the statement of account (`IncubatorStatementDialog`: printed, or a WhatsApp summary a person sends). Pure, tested rules in `lib/`: `summary.ts` (figures to the fils, sale states, a sale's profit for staff who may see costs), `forms.ts` (form values and what stops a save), `errors.ts` (every database code in Arabic and English, never a bare code), `movements.ts` (the history's labels), `statement.ts` (period, totals, the A4 page and the message). Data: `src/lib/data/incubators/` (the history is read a page at a time, when its tab is opened; sales and payments are read whole, to their end, by `readAll`). Partner money is the database's (migration `20261012170000`, run in a real Postgres by `tests/partner-money-migration.test.ts`): a partner's figures come from `incubator_summaries` (`fetchIncubatorSummaries`; never add them up from the loaded sales, the API cuts a list at its row limit), which also says when the last and the next settlement fall for the partner's `settlement_day` and what is overdue (unpaid for sales made before the last settlement, on the reader's own calendar day and time zone); a payment is taken back by `void_incubator_payment` (its sales owe their part again, the payment stays on record with who and why, and is counted nowhere); several pieces go to a partner in one transaction through `transfer_stock_to_incubator_batch` (`transferStockBatchToIncubator`, used by `BatchIncubatorTransferModal`), which names the piece that stopped it (`batchTransferRefusal`). Tests: `tests/incubators-rules.test.ts`, `tests/incubator-page-management.test.tsx`.
  - Variant axes & SKUs: `src/lib/variant-axes.ts`, `src/lib/variant-sku-utils.ts`, `src/lib/variant-i18n.ts`
  - Category listing filters: `src/lib/category-filters.ts` (pure: sizes and colours are multi-select and match on ONE variant, options come from the page's own products with a count each, the "Standard" placeholder size is never offered, filters live in the address as repeated `size` / `color` parameters, written with `replaceUrlQuietly` (`src/lib/quiet-url.ts`): TanStack Router wraps `window.history.replaceState` and treats any call as a navigation that scrolls to the top, so a page that only mirrors its state into the address must not call it); the panel is `CategoryFilters` (and `CategoryFiltersSheet` on phones), the page `src/routes/$slug.$category.tsx`. The product gallery's thumbnails (`ProductGallery`) are equal-size with the choice shown by the border, and nothing in them may move the page (`tests/product-gallery-thumbnails.test.tsx`).
- **Orders & Checkout**:
  - Admin order editor: `src/features/orders/` (`components/` for the cards, dialogs and line editor; `hooks/` for data, save, payment, promo and line actions; `actions/` for print/share and status changes; `lib/` for pure, unit-tested rules such as totals, save payloads and change detection). The route `src/routes/_authenticated/admin.b.$slug.orders.$id.tsx` holds the editor state and layout. Shared order UI: `src/components/orders/`
  - Job sheet (a store that makes to order): the page printed for the workshop with a piece to make, from the order's documents card (`OrderSalesDocumentsCard`, shown only when `createOrderDocumentActions` returns `printJobSheet`). Pure in `src/features/orders/lib/job-sheet.ts`: `isWorkshopLine` (a line marked `custom`, a hand-made custom line, or one with the customer's answers; never a service), `jobSheetPieces` (options in the store's axis words, measurements, the customer's notes, extras) and `jobSheetHtml` (the A4 page, Arabic or English, in the store's word for the workshop). It carries no prices and no contact details (`tests/job-sheet.test.ts`). The same actions offer to tell the customer that work has started (`workshop.tellCustomerWorkStarted`): a WhatsApp message a person sends, written by `workStartedMessage` (`src/features/orders/lib/stage-messages.ts`, with the store's made-to-order estimate when it wrote one), offered in the confirmation after "Send to workshop" and in the documents card while the piece is there, only when the customer has a number WhatsApp can reach; opening it is noted in the order's activity (`tests/work-started-message.test.tsx`).
  - A shopper's account page: `src/features/storefront-account/` (the route `$slug.account.tsx` only mounts `AccountPage`): `components/` hold the page and its sections (`OrdersSection` with `OrderTimelineTracker`, `CustomerReturnsSection`, `ProfileSection`, `AddressesSection`, `SignOutButton`), `hooks/use-customer.ts` the shopper's own customer record, and `lib/account-shared.ts` how an order's state reads to a shopper (`statusMeta`). `tests/storefront-account-rules.test.ts`; `tests/store-profile-surfaces.test.tsx` renders the page.
  - Storefront checkout: `src/routes/$slug.checkout.tsx` (composition) + `src/features/checkout/` (validation, `place_storefront_order` args, hooks, sections); `src/routes/$slug.thank-you.$orderId.tsx`
  - The order builder: `place_storefront_order_internal_20260710` (called by `place_storefront_order`) resolves the customer, saves the delivery address, creates the order and its lines. **`tests/storefront-order-address-migration.test.ts` runs the real function in a real Postgres (PGlite): extend it whenever the function is redefined**; a rewrite that nothing ran once dropped every delivery address and refused signed-in shoppers (fixed by migration `20261012110000`). The rules it holds: `customers.user_id` is the store's owner and the shopper's account is `customers.auth_user_id`; a signed-in shopper is the customer their account is linked to and is never matched to another account's record; the checkout sends the address as fields of `p_customer` (`label`, `region`, `block`, `road`, `house`, `flat`), which is kept on the customer, saved as one of their addresses (the same one is reused) and pointed at by `orders.shipping_address_id`, from which the `capture_order_delivery_address_snapshot` trigger copies it onto the order.
  - How a store is paid is its own switches (`business_settings.cod_enabled`, `card_enabled`, `benefit_enabled`), and **the database holds them, not only the checkout page**: a storefront order (channel `storefront`) written with a method that is switched off is refused with `PAYMENT_METHOD_DISABLED`, and with anything but the three with `INVALID_PAYMENT` (trigger `trg_orders_payment_method_enabled`, migration `20261013160000`, run in a real Postgres by `tests/storefront-payment-method-migration.test.ts`; the checkout words it in `placeOrderFailure`). The order builder once made this check itself and a rewrite dropped it, so a cash order could be placed with a store that takes no cash, and a cash appointment confirmed its day at once. The rule sits on the table so that rewriting a function cannot drop it again; staff orders (channel `admin`) are not touched. How an order is handed over is held the same way (`delivery_enabled`, `pickup_enabled`, `digital_delivery_enabled`: `DELIVERY_DISABLED`, `PICKUP_DISABLED`, `DIGITAL_DELIVERY_DISABLED`), but **when the transaction ends** (the deferred constraint trigger `trg_orders_fulfilment_enabled`, migration `20261013170000`, `tests/storefront-fulfilment-migration.test.ts`): an appointment is written as `delivery` and a digital order as `pickup`, and each is given its own method a moment later, so a check made while the row is written would refuse them. An appointment is never refused by it (a services store that does not deliver still goes to the customer's venue).
  - Payment state: an order says how it is paid in `payment_status` and in `advance_paid` (what was collected), and **no screen writes a payment status by itself**. A transfer (BenefitPay or bank) is validated only by `approve_benefit_payment` (`approveBenefitPayment` in `src/lib/data/orders/mutations.ts`), from the order page and from the list's "Validate payment": the database records the advance of an order placed under an advance rule (`partially_paid`, the balance is due on delivery) or the whole total, who verified it, and it works with or without an uploaded receipt; an approved transfer cannot be rejected. A balance is collected with the hand-over by `courier_complete_delivery` (`courierCompleteDelivery`: the list's cash dialog, the courier page, and the order page's "Collect balance & ..." buttons), which records the amount. `/api/orders/status` changes stages only and refuses a `payment_status`. The database holds the rest (migration `20261012130000`, tested in a real Postgres by `tests/payment-state-migration.test.ts`): `paid` always means `advance_paid = total` and a part payment that reaches the total is `paid` (`trg_orders_payment_amounts`), the first approval (in full or of the advance) releases the hold and tells the customer once, and collecting the balance later does not repeat it. An order whose advance was approved is not "awaiting payment" (`getOrderWorkflow`), it is to be prepared. The order editor's save sends the stage and payment fields only when they were changed in that editor (`orderUpdatePayload`), so a page left open cannot undo an approval made elsewhere. Words for staff: `src/features/orders/lib/transfer-approval.ts`; behaviour: `tests/payment-validation-paths.test.tsx`.
  - An order's two status fields: `status` is what the database reads (the stock engine `order_inventory_desired_state`, the booking that follows its order, the report functions) and `fulfillment_status` is the stage the screens move. **When the stage reaches its end (completed, delivered, picked up) the status is `completed`, whoever wrote the row**: the trigger `trg_orders_status_follows_fulfillment` (migration `20261013100000`, run in a real Postgres by `tests/order-status-follows-fulfillment-migration.test.ts`) holds it; an order that was undone, a draft and an archived one keep their status. The list's "complete" button once wrote the stage alone and left orders at `packing` for good. The app's own figures (cost of goods on the expenses page, the inventory's sales rate) count every order that counts as sold: `countsAsSold` / `NOT_SOLD_ORDER_FILTER` (`src/lib/data/orders/sold-orders.ts`), an exclusion like the report functions use. **Never list the statuses that count**: a list does not know every stage an order passes through.
  - WhatsApp order updates (Meta, a pilot that is switched off): the checkout offers the opt-in only when `storefront_whatsapp_updates_ready(brand)` says the store can send (its own connection in `whatsapp_integrations` is on, has a number, and has an active "order placed" message); `checkoutQueries.whatsappUpdatesReady`, `CustomerDetailsCard`. The consent (`record_order_whatsapp_opt_in`), the queue (`enqueue_order_whatsapp_event`) and the sender's claim (`claim_whatsapp_outbox_event`) follow the store's connection too, never a store's name (migration `20261013110000`, `tests/whatsapp-updates-migration.test.ts`, `tests/checkout-whatsapp-optin.test.tsx`). **Never gate a feature on a store's slug**: ask the setting, the module or the connection. A permanent store is one whose plan is `lifetime` (`plan_type`), in the app and in the two plan functions (`rpc_evaluate_brand_entitlements_unchecked`, `rpc_sync_legacy_brands_to_subscriptions`; migration `20261013130000`, `tests/lifetime-plan-migration.test.ts`): they once also named one store. Three names are left on purpose: the onboarding wizard previews one real storefront as its sample, `MobileAppDownloadsCard` lists the one store that has its own customer app, and `__root.tsx` falls back to that store for its older app builds, which send no store with a push registration.
  - Delivery time: a store writes one estimate for ready pieces (`delivery_estimate_*`) and may write another for pieces made to order (`delivery_estimate_tailored_*`, migration `20261007100000`, fields in `registry-delivery.ts`); `src/lib/delivery-estimate.ts` decides what a shopper reads: the product page by the choice made (a made-to-order piece, unless a ready size is chosen), checkout by the cart (`cartEstimateKinds`, the same reading the advance payment uses), both sentences when a cart holds both kinds, and a made-to-order piece sent to a shipping zone adds the zone's time ("then shipping"). A store that writes no made-to-order text says one thing, as before.
  - Courier: a user whose role is `courier` sees only the deliveries assigned to them. The order route (`admin.b.$slug.orders.$id.tsx`) hands the page to `OrderForRole` (`src/features/courier-delivery/`): a courier gets `CourierDeliveryPage` (amount to collect, one next-step button, call / WhatsApp / maps, the address, what is in the parcel), the office gets the editor, and neither mounts until the profile is known. **Never show a courier the office editor**: its queries (store settings, catalog, customers) are disabled for a courier, so anything waiting on them never finishes. Pure rules in `lib/courier-delivery.ts`; the two actions are `courierConfirmPickup` (through `/api/orders/status`, which lets a courier change the delivery stage only and ignores an `admin_override` flag from anyone who is not an admin) and `courierCompleteDelivery` (the `courier_complete_delivery` RPC, which records what was collected). The shell hides the office's New button and mobile dock from a courier (`tests/courier-delivery.test.tsx`).

## 6. Core Domain Concepts

1. **Store Verticals & Addon Packs** (`src/lib/verticals/registry.ts`, `src/lib/store-profile.ts`, `src/lib/addons/addon-registry.ts`): Stores belong to business verticals (`business_settings.store_vertical`: `fashion` › `abayas`, `beauty` › `fragrance`, `food` › `coffee`, `jewelry`, `gifts`, `print`, `services`, etc.; `electronics` is legacy: valid, not offered). The vertical registry is the single source for each vertical's name, summary, icon, parent, status, modules and starter pack; add a vertical there (tests/vertical-registry.test.ts checks every per-vertical table covers it). A child vertical (abayas under fashion, coffee under food) gets its parent's add-ons: match add-on `activities` with `verticalFits`, never `activities.includes(vertical)`, and list verticals in pickers with `pickerVerticals`. Verticals determine starter packs, default design presets, and category templates. The vertical is set by the platform: only a super admin (or trusted server code) can change it, enforced by the `guard_store_vertical` trigger; brand staff manage their add-ons. A change goes through the super admin's change dialog (`src/components/settings/VerticalChangeDialog.tsx`): the pure planner `src/lib/verticals/vertical-change.ts` previews it, then `changeBrandVertical` installs the add-ons the new vertical needs and the `apply_brand_vertical_change` RPC applies the rest in one transaction and records it in `brand_vertical_changes` with a reason. Never write `store_vertical` from a settings form. The planner also lists what a change leaves behind (`src/lib/verticals/vertical-leftovers.ts`: hand-set module overrides, goods left in a services store, open orders and bookings, incubators, returns, delivery settings; nothing is deleted). Admin screens are gated by module, never by vertical name, and data stays reachable while it exists; the rules, what was fixed and what is still to do are in [`docs/vertical-fit-audit.md`](./docs/vertical-fit-audit.md).
2. **Dynamic Variant Option Axes** (`src/lib/variant-axes.ts`): Variants store options in generic columns (`size`, `color`, `fabric`, `option_four`, `option_five`) whose meaning depends on the store (a roastery keeps the roast level in `color`). **Never label or render an option by its column name**: resolve labels and swatch-vs-chip rendering with `useVariantAxes` / `describeVariantAxes`, which combine the store vertical, installed addon packs and per-product label overrides.
3. **Hero Media Pipeline** (`src/lib/hero-media.ts`, `docs/media-video-pipeline.md`): Media items can be image or video. Videos are transcoded in-browser using WebCodecs + `mediabunny` into faststart MP4s. Resolvers choose optimal dimensions and crop focal points.
4. **Store Vocabulary** (`src/lib/store-vocabulary.ts`): Terminology adapts per vertical (e.g. "Abayas" vs "Products", "Tailoring" vs "Customization").
5. **Storefront Modes** (`src/lib/storefront-mode.ts`): Brands operate as a full shop with checkout (`shop`) or as a catalog (`catalog`): products shown with or without prices (`catalog_show_prices`) and a WhatsApp inquiry instead of checkout.

## 7. Architecture & Coding Rules

- **Vanilla Core Isolation**: Core files (`src/routes`, `src/components`, `src/lib`) **must never import from `@/addons/*` directly**. Enforced by ESLint restricted imports. Addons mount via `<AddonSlot />` or `@/lib/addons/*` bridge data.
- **Design Tokens**: Never hardcode hex colors or arbitrary pixel radii. Use semantic tokens (`bg-primary`, `text-muted-foreground`, `border-border`). Follow [`.agents/rules/AGENTS.md`](./.agents/rules/AGENTS.md).
- **RTL & Bilingual**: All UI components must support Arabic (RTL) and English (LTR). Use logical margins/padding or direction-aware flex layouts.
- **A store's money is written in the store's currency**: `business_settings.currency`. On an admin screen read it with `useStoreCurrency(brandId)` (`src/hooks/use-store-currency.ts`) and pass it to `formatMoney`; a label or a field's tag that names the currency ("Price (BHD)") uses `useMoneyLabel(lang)` or the pure `currencyLabel(currency, lang)` (`src/lib/currency-label.ts`: the code in English, the short form Arabic readers know in Arabic). An amount that belongs to an order or a return is written in that order's own currency. Never write `"BHD"` or `د.ب` on a store's screen: the accounting tabs, the returns dialogs, a customer's page and some twenty-five labels once did (`tests/store-currency.test.tsx`). The platform's own prices (subscriptions, add-ons) are in BHD by design.
- **A period of days is sent as moments**: a screen's period is whole days (`YYYY-MM-DD`) on the reader's own clock, and a row's time (`created_at`) is a moment. A bare day sent to the database is read at midnight UTC, so in Bahrain an order placed between midnight and 03:00 on the 1st fell in the month before (the expenses page's cost of goods did this). Turn the days into bounds with `localDayRange` (`src/lib/day-range.ts`: from the first day's midnight, to before the midnight after the last) and compare with `gte` / `lt`; the report functions do the same with moments and the reader's time zone (`p_tz`), so the two agree. A column that is itself a day (`expense_date`, `event_date`) is compared as a day (`tests/day-range.test.ts`).
- **Shared Resolvers Over Surface-Specific Hacks**: Never duplicate resolution logic in a route; place canonical logic in `src/lib/` (e.g., `resolveHeroMedia`, `calculateStock`).
- **A list is read to its end, or says how many rows it wants**: the API answers a list with at most its row limit (1,000 rows) and does not say that it stopped, so a store's 1,001st variant, customer or order was simply not there: a total was short, a cost read as zero, an import made duplicates, an export lost its tail. A reader whose caller treats the result as the whole list goes through `readAll` (`src/lib/data/read-all.ts`): its page function asks for one range in a fixed order that ends on a unique column (`.order("id")`) with `{ count: "exact" }`; a list that fits costs one request, as before, and a longer one is read whole (the count says how much is left, and the rest is asked for at once). Any other list read says its bound: `.limit()`, `.range()`, one row, or a list of ids. The ratchet counts list reads with neither (`unboundedListReads` in `scripts/maintainability-metrics.mjs`, `tests/maintainability-ratchet.test.ts`): what is left is settings-sized tables and one parent's rows, and the number only goes down. The lists a screen holds whole (the inventory's products and variants, the orders list, customers) are filtered and paged in the browser on the complete list: that is right for a boutique's thousands of rows; moving a list's filters and counts into SQL would need a second copy of its rules (`tests/read-all.test.ts`).
- **Data Access Layer** (`src/lib/data/`, see its README): reads and writes live in one module per domain with `selects.ts` (column lists), `keys.ts` (query-key factories), `queries.ts` (fetchers + `queryOptions`) and `types.ts`. Screens call `useQuery(xxxQueries.foo(...))` and never build keys or queries by hand. Migrated so far: the public storefront catalog (`storefront/`); admin orders reads + writes (`orders/`, incl. finance, COGS and reconciliation views); `business-settings/`; `expenses/`; admin catalog reads + writes (`catalog/`: products, variants, stock, BOM, packaging, add-ons); customers and saved addresses, admin and storefront (`customers/`); settings writes (`business-settings/`, `brands/`). ESLint `no-restricted-syntax` enforces them on the storefront routes and slices, and on the orders, dashboard, accounting, expenses, inventory, customers and settings screens (no direct `from(...)` for those tables, no hand-built keys). Also `returns/` and `reporting/` for the dashboard, admin `categories/`, `loyalty/`, `promo-codes/`, `incubators/`, `message-templates/` and `profiles/` (the route guards' caller profile). `returns/` covers the admin returns screens too; `push/` the push centre; `notification-recipients/` the admin alert recipients; `media-optimizer/` the super admin video re-optimizer; `abandoned-carts/` the admin abandoned-carts screen; `integrations/` the integrations screen; `super-admin/` the super admin's platform screens; `import-export/` the import and export history; `checkout/` the storefront checkout's calls; `addons/` the addon data core screens read; `activity-logs/` the activity log; `system-settings/` the platform settings row; `branches/` a brand's branches (admin and checkout pickup); `reviews/` order reviews (admin and public); `brands/` the brand lookups (admin route guard, switcher, onboarding, storefront host); `reporting/` the Reports pages (one overview cache shared with the dashboard). `accounting/` covers the expenses page's cash accounts, vendors and purchase orders tabs. `content-drafts/` holds the content studio's saved drafts. `bookings/` holds a services store's booking rules, bookings, blocked days and public availability (writes go through the booking functions; pure rules in `src/lib/bookings/rules.ts`). `verticals/` holds a store's vertical change history and the change preview. Session reads and sign-out go through `@/lib/auth/session` (`getCurrentUser`, `getCurrentSession`, `getAccessToken`, `signOut`; route guards use `ensureSessionUser`). The sign-in flows (password, passkey, Google, storefront sign-up and membership, recovery, first login, passkey management) go through `@/lib/auth/sign-in`, which returns Supabase's results unchanged. ESLint forbids `supabase.auth.*` in routes, components and features. Still direct: the server routes (`src/routes/api.*`, the manifest route), and the order editor's realtime subscription. Method: [`.agents/skills/data-layer-migration`](./.agents/skills/data-layer-migration/SKILL.md); status and next steps: [`docs/agent-handoff.md`](./docs/agent-handoff.md).

## 8. Database & Security Rules

- **Production Database**: Linked to remote Supabase. Treat as **read-only** by default (`npx supabase db query --linked "<select>"` is fine). Never execute `db reset`, `db push`, `migration repair`, or unvetted DDL; the owner applies migrations (`npx supabase db push --linked`) after reviewing a `--dry-run`.
- **Who may open a page of a store's admin**: one table, `PAGE_ACCESS` in `src/lib/page-access.ts` (the page is the first part of the address after the store; a rule is a permission a member of staff needs, or admins only), held by one guard in the admin layout's `beforeLoad` (`admin.b.$slug.route.tsx`: `mayOpenPage`; a courier has `orders` and nothing else; whoever may not open a page is sent to one they can, `homePageOf`). Five pages once carried their own copies of the check, with small differences, and the others had none: the menu hid a page and its address still opened it. **A new page gets a row in the table, not a guard of its own**; the menu item carries the same rule. `tests/page-access.test.ts` keeps the table, the route files and the menu equal, and `tests/super-admin-platform-navigation.test.tsx` runs the guard. This decides what a person is shown; what data comes back is the database's rules (next line). The platform's owner is known in the app by one constant, `SUPER_ADMIN_EMAIL` (`src/lib/profile-context.tsx`), and in the database by role.
- **Row Level Security (RLS)**: Every multi-tenant table enforces RLS. Security functions live in Postgres (`can_access_brand`, `is_brand_owner`, `is_super_admin`). Always scope queries by `brand_id`.
- **Function grants (RPCs)**: a SECURITY DEFINER function is callable by the browser unless its grant is removed (Supabase grants EXECUTE to `anon`, `authenticated` and `service_role` on every new function), so a function that only the server calls (secrets, payment state, quotas) must be revoked from `anon` and `authenticated` in the migration that creates it, and a function the browser does call must check the caller inside. Never write the check as `IF auth.uid() IS NOT NULL AND NOT can_access_brand(...)`: it is skipped for an anonymous caller. The first clean-up is `20261007110000_revoke_browser_access_to_server_functions.sql` (tested in a real Postgres by `tests/revoke-browser-access-migration.test.ts`); `20261007140000_loyalty_and_coupons_server_side.sql` moved loyalty award/redeem to the server: the browser asks `src/lib/loyalty-checkout.functions.ts` (`redeemLoyaltyForOrder`, `awardLoyaltyForOrder`), which checks the order is the signed-in shopper's and calls the database as the service role. Redeeming points lowers the order's own total in one transaction (`redeem_loyalty_points_for_order`, migration `20261007150000`: discount and total like a promo code, `orders.loyalty_points_redeemed` / `loyalty_discount`); before that the points discount was only drawn in the checkout summary.
- **Guard**: `supabase/function-grants.json` lists every SECURITY DEFINER function a browser (`anon` or `authenticated`) can call, with the reason; `npm run db:function-grants:check` (and the CI job "Supabase Linked Migration Drift Check") reads the live database and fails on one that is not listed, so a new function that only the server calls must be revoked in its migration (apply the migration first, as always) and one a browser calls must check the caller inside and be listed. `tests/function-grants-guard.test.ts` keeps the list honest and bans the fail-open check from new migrations. The same check fails on a read policy written `TO anon` that calls a function a visitor cannot execute (e.g. `USING (is_active OR can_access_brand(brand_id))` made every visitor read of `advance_payment_rules`, the FAQ and the gallery fail with "permission denied for function"; migration `20261009130000`): keep a visitor policy to plain columns and give staff their own policy `TO authenticated` (tested in a real Postgres by `tests/visitor-read-policies-migration.test.ts`).
- **A public server function is careful with what it pays for and what it stores**: `translateOptionTerms` (`src/lib/translate-options.functions.ts`) is called from a shopper's page, so anyone can call it. It looks only at short words (`translatableTerms`), sends the paid model only the words a store really sells under (`catalog_option_values`, service role only: an option value of a variant, or a product's fabric or occasion), keeps of the answer only a short translation of a word that was asked (`acceptedTranslations`), and does not store what the built-in lexicon already answers. The shared `translation_cache` is written by the server only: the policies that let any signed-in account, a shopper's included, rewrite a row are gone (migration `20261013120000`, `tests/translate-option-terms.test.ts`). A new server function with no auth middleware needs the same thought: what can a stranger make it spend, and what can they make it keep.
- **What a visitor may write**: an insert policy `WITH CHECK (true)` lets anyone write any row, of any size, as often as they like. A table only the server writes has no browser policy and no browser INSERT grant (`tenant_requests`: the form saves through `onboarding.functions.ts`, which checks and rate-limits). A table a visitor does write (`shared_carts`) gives the browser INSERT on the columns a visitor sets and nothing else (the expiry is the table's default), holds CHECK constraints for the row's shape and size, is read through a function, and has a nightly job for what expires (`delete_expired_shared_carts`, pg_cron `shared_carts_cleanup_nightly`). Migration `20261013140000`, tested in a real Postgres as a visitor by `tests/public-writes-bounded-migration.test.ts`. The same care for a server function anyone can call: one that fetches an address for its caller (`getInvoiceAssetDataUrl`) fetches only from the platform's own hosts, follows no redirect and stops at a byte limit (`src/lib/invoice-asset-rules.ts`, `tests/invoice-asset-rules.test.ts`).
- **Costs are for staff who may see the store's finances**: a product's and a variant's costs live in `product_costs` / `variant_costs`, read and written only by `can_view_brand_costs(brand)` (the store's staff holding `view_financials`, like the expenses, suppliers and purchase orders; migrations `20261007170000`, `20261008100000` and `20261013150000`). A member of staff without the permission reads no cost, so their screens show no cost field (`ProductCostField`, the variant rows, the packaging dialog's direct cost) and, because a form that cannot read a cost holds zero, **the database keeps the cost columns as they are when such a person saves** (`trg_products_keep_costs`, `trg_product_variants_keep_cost`: the rest of the save goes through; a new product starts with no cost and a new variant takes its product's). The server and the database's own functions are not held back. Run in a real Postgres as an owner, a stock clerk and the server by `tests/costs-financial-permission-migration.test.ts`; screens in `tests/cost-fields-permission.test.tsx`. Still open to any office staff, on purpose for now: an order line's cost snapshot (`order_items.unit_cost`) and the packaging materials' unit costs (an inventory matter). The old cost columns on `products` / `product_variants` stay for writes (triggers copy them across) but `authenticated` and `anon` cannot SELECT them, so **never `select("*")` on those two tables**: the admin reads named columns (`src/lib/data/catalog/selects.ts`, kept equal to the generated types by `tests/catalog-admin-columns.test.ts`) and merges costs in with `src/lib/data/catalog/costs.ts`. A column added to either table needs `GRANT SELECT (col) ON public.<table> TO authenticated;` in its migration; `npm run db:catalog-columns:check` (CI) fails otherwise.
- **Additive Migrations**: Schema changes must be backward-compatible, sequential SQL scripts in `supabase/migrations/`. Check with `npm run db:migrations:check`. Local and production history match (zero drift); CI fails a PR whose migration is not applied yet, so apply (owner) → verify → regenerate types → open the PR.

## 9. Maintainability Ratchets & Quality Gates

Maintained in [`tests/maintainability-ratchet.test.ts`](./tests/maintainability-ratchet.test.ts); current numbers in [`docs/maintainability.md`](./docs/maintainability.md):

- **Ceilings move only down**: `as any`, `: any`, `as never`, `@ts-ignore`, `eslint-disable`, direct Supabase calls, and brittle `readFileSync` test files are strictly capped. Increasing any count breaks CI.
- **Giant File Freeze**: Existing files $>1,000$ lines cannot grow. New files must stay under **600 lines**.
- **Behavior Testing**: Never test a feature by reading its source text. Call the pure function (extract it into `src/lib/` or the feature's `lib/` if needed) or render the component with its data layer mocked. Server functions and middleware run in tests through [`tests/helpers/server-fn.ts`](./tests/helpers/server-fn.ts) (a recording `createServerFn` and a fake Supabase client). `readFileSync` is left only for SQL / edge-function contracts and architecture guards; see [`docs/behaviour-tests.md`](./docs/behaviour-tests.md).
- **Pull Requests**: Fill in the checklist in [`.github/pull_request_template.md`](./.github/pull_request_template.md) (quality gate, ratchet, behaviour tests, data layer, RTL, screenshots, owner-applied migrations, bug backlog).

## 10. Known Pitfalls

- **Vitest Memory & Worker Timeouts**: Full test suite (`npx vitest run`) executes 1,000+ tests. Run specific files during development: `npx vitest run tests/<file>.test.ts`.
- **JSDOM Stubs**: Browser globals like `scrollIntoView`, `matchMedia`, and `window.open` are stubbed in [`tests/setup.ts`](./tests/setup.ts). Add mocks there if needed.
- **No Network in Unit Tests**: [`tests/setup.ts`](./tests/setup.ts) rejects every `fetch` and WebSocket, because the Supabase client points at production. Mock the data layer; `vi.mock` needs the relative path (`../src/lib/data/x`) as well as the `@/` alias, or the real module runs and its request is refused. CI has no Supabase environment (locally `.env` hides this): a test that lets real code build `@/integrations/supabase/client` passes locally and fails in CI, so mock it and try new tests with `.env` moved aside.
- **Windows vs POSIX Paths**: In scripts, always normalize backslashes (`path.replace(/\\/g, "/")`). Avoid unescaped `$slug` variables in PowerShell commands.
- **Content cut off at the side of a phone**: html, body and the page shells hide sideways overflow, so a block that grows wider than the screen is not scrolled to, it is cut off (the checkout lost the edge of every field when a product name was long), and `document.scrollWidth` says nothing. Three guards: (1) a grid with no columns of its own is one implicit `auto` column that cannot be narrower than its widest content, so `src/styles/layout-guards.css` sizes it `minmax(0, 1fr)` for every such grid; (2) in an arbitrary template write `minmax(0,1fr)`, never a bare `1fr` (`tests/design-system-guardrails.test.ts` fails on one); (3) the overflow audits open every storefront page and every admin screen (a store's and the platform's) at 320px and 390px, in Arabic and English, with long names and a word that cannot wrap, press each page's buttons to open its dialogs, drawers, menus and tabs, and measure the boxes (`tests/storefront-overflow-audit.spec.ts`, `tests/admin-overflow-audit.spec.ts`, rules in `tests/helpers/overflow.ts`). They take about half an hour, so they are **on demand, not part of the pull-request checks**: `npm run audit:overflow` (`-- --stores=zh,pura`, `-- --screens=orders,settings`, `-- --admin`, `-- --storefront`); run it after layout work on a page, and put a new admin screen in its list. A row of buttons needs `flex-wrap`; a native `<select>` is as wide as its longest option, so give it `max-w-full`.
- **Text cut short**: a name (a product, a customer, an order line, a store) is never cut to one line: `line-clamp-2 break-words`, and in a product grid `min-h-[2lh]` as well so two lines are always reserved and a row's prices line up (`ProductCard`, `ProductCardV2`). A name whose language may differ from the page's takes `dir="auto"` with `text-page-start` (`src/styles/layout-guards.css`), so an English name on an Arabic page is cut at its own end and still sits at the page's start edge. `truncate` is for secondary lines only, and whatever is still cut anywhere can be read in full: `TruncationReveal` (`src/components/ui/truncation-reveal.tsx`, mounted once in `__root.tsx`, rules in `src/lib/truncation.ts`) shows the whole text beside it on a rest of the mouse, a tap on plain text, a long press inside a link or a button, or keyboard focus; `data-no-reveal` opts an element out. `tests/design-system-guardrails.test.ts` fails on a product title cut to one line and caps the number of `truncate`s.
- **Long text in a flex row**: a `truncate` element only truncates when every flex ancestor up to the box has `min-w-0` (a flex item's minimum width is its content's, so one URL or file name pushes the row past its box). `DialogContent`'s single column is `minmax(0,1fr)` for the same reason; give a row inside a card its own `min-w-0 flex-1`.
- **Generated Files**: **Never manually edit** `src/routeTree.gen.ts` (generated by TanStack Router) or `src/integrations/supabase/types.ts` (generated by Supabase CLI).
